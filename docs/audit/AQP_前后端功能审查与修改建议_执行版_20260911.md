## 1. 先看结论

AQP 已经不是功能原型，而是一套具有完整量化研究流程的全栈平台，当前覆盖行情、个股、ETF、选股、回测、研究、因子工作室、数据中心、训练前置、执行中心、预警、日报和系统设置。

当前最值得投入的工作不再是继续堆功能，而是把已有功能变成可控、可恢复、可解释的生产能力。建议按以下顺序推进：

1. 先完成公开计算接口的安全策略确认，并把资源预算、限流和审计补齐。
2. 关闭数据中心页面的最后一个数据装载闭环，随后治理 20 至 30 秒冷算和目录扫描。
3. 统一长任务、轮询、错误码和前后端类型契约。
4. 最后再处理 localStorage 服务端化、包体积、Docker 生产化等体验和运维事项。

## 4. 修改优先级与执行任务

优先级定义：

- P0：有安全、数据一致性、核心回归或资源耗尽风险，应优先处理。
- P1：不一定立即造成事故，但会限制生产稳定性、性能或维护效率。
- P2：体验、成本和长期治理优化，可在 P0/P1 稳定后处理。
- D：Decision，先确认产品口径，再决定是否编码。

### P0-1：为公开计算接口建立正式访问策略

状态：待修改，属于“策略未完成”，不是简单的漏挂依赖。

当前运行时注册表把以下 15 个写/计算接口标为公开，见 backend/tests/test_write_endpoints_smoke.py 的 PUBLIC：

- 回测：/backtest/run、/backtest/strategy-run、/backtest/signal-analysis
- 研究：/research/factor-icir、factor-corr、factor-quantile、cv-folds、optimize、impact-sim、stress-test
- 组合和执行分析：/portfolio/backtest、/desk/attribution
- 导出：/export/backtest、/export/strategy-backtest

风险：

- 未登录调用者可能持续占用 CPU、内存、磁盘和外部数据源。
- 导出接口可能把计算结果或路径信息暴露给不应访问的调用者。
- 即使接口本身是只读，POST 仍可能造成高并发资源消耗。

建议修改顺序：

1. 先按部署模式确认策略：本机单用户可以保留部分公开接口；共享部署至少要求 viewer 登录；研究计算、参数寻优、导出和压力测试建议要求 researcher。
2. 对需要登录的接口添加 Depends(require_role(\"viewer\")) 或 Depends(require_role(\"researcher\"))。
3. 对回测和研究计算增加请求预算：最大日期跨度、标的数、并发数、单用户速率限制和结果缓存。
4. 对导出增加权限校验、文件下载过期时间和审计日志。
5. 修改 test_write_endpoints_smoke.py 的注册表，让测试继续强制校验运行时策略，而不是把当前公开状态永久固化成安全结论。

验收条件：

- 未登录、viewer、researcher、admin 的访问行为和端点矩阵符合产品决定。
- 每个计算接口都有最大输入规模和超限错误码。
- 同一用户并发重复提交不会无限增加后台线程。
- test_registry_matches_runtime_rbac 仍通过。

### P0-2：收紧生产认证配置

证据：

- backend/app/core/config.py:152 定义默认 ADMIN_TOKEN = aqp-dev-token-change-me。
- backend/app/core/config.py:167-173 当前主要记录告警，不会在生产启动时强制失败。
- backend/app/core/auth.py:114-122 允许持有 ADMIN_TOKEN 的请求直接成为 admin。

风险：如果生产部署忘记注入 .env，默认凭据可能直接获得最高权限；如果没有独立 JWT_SECRET，JWT 密钥可由 admin token 推导。

建议修改：

1. 增加明确的 ENV 或 APP_ENV，生产值使用 prod。
2. 生产启动时强制要求：ADMIN_TOKEN 非默认值、JWT_SECRET 已设置且长度足够、CORS/host 配置不为开发宽松值。
3. 将静态 token 直通限制为开发模式，或者由 ALLOW_ADMIN_TOKEN_LOGIN=false 显式控制。
4. 兼容旧版 AQP_ADMIN_TOKEN 时，在开发环境迁移；生产环境不允许前端长期保存 admin token。
5. 增加启动配置检查测试，分别覆盖开发配置可启动、生产弱配置启动失败。

验收条件（PowerShell 示例）：

    $env:ENV = "prod"
    $env:ADMIN_TOKEN = "aqp-dev-token-change-me"
    $env:JWT_SECRET = ""
    # 启动应用，预期应失败或明确拒绝，而不是只写 warning

同时应验证：JWT 不能用旧 token 派生密钥伪造，admin token 失效后旧会话不能继续获得 admin 权限。

### P0-3：保证核心测试链路长期可运行

当前补测已经通过测试隔离，最新报告为 553 passed / 5 skipped。此前本机曾因应用导入阶段预加载 Torch 触发 Windows 原生崩溃，因此该风险仍需要保留为回归防线，而不是认为已经永久消失。

重点位置：backend/app/__init__.py、训练 readiness、backend/tests/conftest.py。

建议修改：

1. 应用基础导入路径不要无条件加载 Torch/XPU。
2. 训练能力检测默认走子进程探针，探针崩溃只影响 readiness，不得杀死 API 主进程。
3. 使用 AQP_PRELOAD_TORCH=false 作为默认值，训练环境再显式开启。
4. Torch 专项测试加 marker，普通 API、缓存、权限和数据测试不依赖 Torch。
5. 将测试隔离说明写入贡献文档，禁止测试默认写入生产 data、模型和 SQLite。

验收条件：

- 无 Torch、Torch 导入失败、Torch 原生崩溃三种情况下，普通 API 测试都能完成并给出可读结果。
- pytest 单文件、全量、随机顺序运行都不会写入生产目录。
- ruff、mypy、pytest 纳入 CI，并输出明确的失败阶段。

### P0-4：把错误响应契约真正统一

当前项目已经有 APIResponse 和 ERR_PARAMS，但历史上出现过裸字面量错误码和裸 500。新增端点必须遵守同一规则。

建议修改：

1. 所有业务拒绝统一经过 AQPException 或 fail()，禁止在路由中直接返回自定义裸字面量。
2. 错误码集中登记在 backend/app/core/errors.py，每个码有名称、HTTP 语义、用户提示和是否可重试字段。
3. 对文件不存在、数据为空、外部源失败、权限不足、任务冲突分别建立稳定错误码。
4. 增加自动检查：扫描路由源文件中的 fail(数字) 和未包装的 HTTPException，发现新增违规即 CI 失败。
5. 对导出接口这类非 JSON 响应明确记录异常格式，不能假设所有接口都有统一信封。

验收条件：所有正常业务失败均包含稳定 code/message/data；未知异常才返回系统错误，且日志包含 request id 和堆栈。

## 5. P1 稳定性与性能整改

### P1-1：闭环数据中心 /data 页面

背景：补测发现 /datacenter/overview、/settings 的接口可以返回真实统计，但 /data 页面一度出现统计值为 —、资产清单不加载或间歇超时。当前代码在 frontend/src/pages/DataCenter/index.tsx:399-425 已通过 Promise.allSettled 同时加载 overview、datasets、quality、logs、task-stats、status 和 autoStatus，因此需要以当前代码做一次真实浏览器复核，不能继续沿用旧现象直接下结论。

建议排查顺序：

1. 打开 /data，记录首屏每个请求的开始时间、结束时间、HTTP 状态、业务 code 和响应数据。
2. 确认 overview 成功时四个摘要值都进入 React state，datasets 成功时资产清单数量大于 0。
3. 确认某个请求失败时不会因为 Promise.allSettled 的一个 rejected 结果清空其他成功结果。
4. 为每个面板增加独立 loading/error/empty 状态，不使用整个页面一个 error 覆盖所有成功数据。
5. 增加 Playwright 回归：冷缓存首次进入、缓存命中再次进入、overview 失败但 datasets 成功、datasets 失败但 overview 成功四种场景。

验收条件：

- 后端返回真实值时，页面不显示 —。
- 单个面板超时不会让其他面板回退为空。
- 首次冷算在合理等待时间内显示“正在扫描”而不是笼统“网络错误”。
- 任务结束后只刷新必要的统计，不重复加载所有静态数据。

### P1-2：治理 overview 冷算和目录扫描

证据：

- backend/app/api/v1/datacenter.py:195-205 的 _scan_all_datasets 和 _dir_size 涉及大量文件。
- backend/app/api/v1/datacenter.py:217-232 的 overview 冷路径约 27 至 30 秒。
- 镜像状态已经增加缓存，但 _dir_size(DATA_ROOT) 仍可能每次遍历目录。

建议修改：

1. 给 _dir_size 增加 TTL 缓存，并在同步任务完成后主动失效。
2. 避免每次请求逐文件读取 parquet；同步时维护数据集统计表或 manifest，overview 只读统计表。
3. 将 storage_gb、数据集数量、覆盖标的、最新日期拆成轻量摘要接口，详情扫描异步刷新。
4. refresh 按钮显示“正在重扫”，不要让请求线程承担不可预期的全量扫描。
5. 为扫描增加 Prometheus 指标：扫描文件数、扫描耗时、缓存命中、最后成功时间、失败原因。

建议目标：

- 缓存命中：小于 200 ms。
- 常规页面进入：小于 2 s 返回摘要。
- 强制 refresh：可以异步完成，页面先返回上次成功值和 refreshing=true。

### P1-3：长任务从 FastAPI 进程内调度逐步迁出

证据：

- backend/app/main.py:55-72 在 lifespan 中创建晚间例行、启动补跑、预警、自动同步和 overview 预热任务。
- backend/app/main.py:80 负责 shutdown cancel。
- backend/app/services/sync_service.py:472-484 仍是进程内调度和 asyncio.to_thread。

当前实现可以支撑单进程开发环境，但多 worker 或进程重启后有以下风险：重复执行、状态丢失、取消不彻底、失败重试不统一。

推荐分两步：

第一步，单机增强：

- 用 SQLite lease 或数据库任务锁记录 job_name、owner、acquired_at、lease_until、status。
- 启动任务前抢 lease，退出和异常时释放或过期。
- 将任务状态写入持久层，包含 queued、running、succeeded、failed、cancel_requested、cancelled。
- 所有 API 返回 task_id，不要依赖进程内变量作为唯一状态。

第二步，生产架构：

- FastAPI 只负责提交任务、查询任务、取消请求。
- 独立 worker 负责同步、训练、回测、报告和导出。
- 可选 Celery、RQ、APScheduler 或现有基础设施，但必须保持统一任务协议。

验收条件：

- 两个 API worker 同时启动时，同一调度任务只执行一次。
- API 重启后仍能查询已提交任务的最终状态。
- 页面刷新后能恢复任务进度，不会把运行中的任务误显示为失败。
- cancel 是“请求取消”还是“已取消”有明确状态，不伪装成瞬时强杀。

### P1-4：研究、回测、训练页面改成任务化和懒加载

现状：研究页历史上存在首屏一次触发多个计算请求的问题；回测和参数寻优也可能同步占用请求线程。

建议修改：

1. 首屏只加载 overview 和轻量摘要。

## 7. 量化策略与 AI 推荐准确率专项

结论：可以继续提高，但第一目标不应是把一个“准确率百分比”做大，而是先让预测目标、评估指标、推荐候选、交易回测和线上反馈使用同一套口径。当前系统已经有较好的基础：后复权标签、时间切分、embargo gap、LightGBM、特征版本、模型注册表、promote 门禁、RankIC/ICIR 和 PSI 监控都已经存在。下一步应把这些能力串成“研究发现 → 样本外验证 → 推荐生成 → 成本后回测 → 线上监控 → 退化回滚”的闭环。

### 7.1 当前模型和推荐功能的真实基线

| 项目 | 当前实现 | 判断 |
| --- | --- | --- |
| 训练标签 | train_lgbm.py 使用 labeling.build_forward_return_labels，默认预测 5 个交易日的后复权收益；支持极端值治理和 xsec_demean。 | 基础口径较好，但需要补多周期标签和经济意义指标。 |
| 时间切分 | train、gap、valid、gap、test，gap 默认等于 horizon；特征筛选只使用 train。 | 已有防泄漏基础，仍需补滚动 walk-forward 重训验证。 |
| 生产模型 | LightGBM 通过 model_registry 显式 promote；当前生产预测主链路是 LGBM。 | 生产治理比模型数量更重要，暂不建议直接把 GNN/TFT 接入生产。 |
| 模型指标 | 近期报告记录候选模型 valid RankIC 0.1020、ICIR 0.885，并通过 promote；分年稳定性曾出现 2025 RankIC -0.0078、2026 +0.0241。 | 说明模型存在信号，但跨年份稳定性仍不足，不能只看一个验证窗口。 |
| 首页 AI 准确率 | market.py 的 _build_ai_stats 比较 pred_score 正负与 daily_bar 次日收益正负；最近观测约 0.4979，样本约 30377。 | 这个数字接近随机，且与 5 日训练标签不一致，不能称为模型整体准确率。 |
| 单股 confidence | predict.py 使用 clip(0.5 + 2 × valid_rank_ic)，同一生产模型下所有个股基本同值。 | 当前是模型级置信度，不是个股上涨概率；应继续保持明确披露并逐步校准。 |
| 推荐排序 | market.py 的 _build_recommend 直接读取 predictions 按 pred_score 排序；screener.py 另有 ST/停牌/板块过滤。 | 推荐榜和选股榜存在候选口径分叉，需要统一可交易性过滤。 |
| 因子接入 | 因子工作室可以评估、入库和生成报告，但现有报告注明自定义因子暂未自动进入 LGBM 特征空间。 | 因子研究成果尚未形成受控的模型特征注册流程。 |

### 7.2 P0-Q1：先修正“准确率”评价口径

当前最优先的改动是停止把“次日方向命中率”作为唯一 AI 准确率。该指标有三个问题：

1. 训练目标是 5 日后复权收益，线上统计却用次日 raw daily_bar 收益。
2. 它是所有股票和日期池化后的 sign 命中率，不是每日截面命中率，也不是 Top-K 推荐命中率。
3. pred_score 接近 0 时的正负号非常敏感；没有披露零值、样本覆盖、交易成本、置信区间和基准比较。

建议把 AI 统计改成按预测 horizon 返回多组指标：

| 指标 | 口径 | 是否适合对外展示 |
| --- | --- | --- |
| daily RankIC / ICIR | 每个交易日横截面预测排序与对应 horizon 前向收益的 Spearman 相关 | 适合，主指标 |
| Top-K precision | 每日 Top-K 中前向收益大于 0 的比例，同时展示 K 和 horizon | 适合，直观指标 |
| Top-K excess return | Top-K 等权收益减基准或全市场等权收益 | 适合 |
| Long-short spread | Top 分位减 Bottom 分位，扣除交易成本前后分别展示 | 适合 |
| net Sharpe / max drawdown | 按真实换手、滑点、冲击成本和涨跌停规则回测 | 适合策略页 |
| direction hit rate | 只作为辅助指标，必须明确 horizon、价格口径和样本覆盖 | 不应单独称为准确率 |
| calibration | 只有在模型输出概率后才展示 Brier/ECE；当前回归分数不能直接当概率 | 暂不对当前 score 直接套用 |

实施步骤：

1. 在 predictions 中保存 label_horizon、label_price_basis、feature_version、model_version 和 as_of。
2. 将 _build_ai_stats 拆成按 horizon 计算的评估函数，训练标签和评估价格统一使用 hfq 或明确的可交易价格映射。
3. 评估时按日期先聚合，再计算均值、标准差、有效交易日数、覆盖率和 block bootstrap 置信区间，避免大股票池日期权重过大。
4. 对 Top-K 同时输出 K=10、50、100，避免只对一个 K 调参。
5. 把“准确率”字段改名为 directional_hit_rate，并在前端显示“方向命中率”，旁边展示 RankIC、Top-K 超额收益和评估窗口。

验收条件：

- 5 日模型的线上评估默认使用 5 日标签，不再默认拿次日收益替代。
- 训练 metrics、research/lab/yearly、首页 AI stats 三处指标可以由同一份评估函数复算。
- 每个指标都带 horizon、as_of、样本数、有效日期数和数据口径。
- 旧的 49.79% 方向命中率不再被前端单独解释为“AI 推荐准确率”。

### 7.3 P0-Q2：统一 AI 推荐和选股的候选链路

market.py 的推荐榜直接从 predictions 排序，screener.py 则会调用 data.screening.filter_universe 处理 ST、停牌和板块。建议新建一个共享的 recommendation_candidates 层，让首页推荐、选股页、预警和回测都消费相同的候选快照。

候选过滤建议分为三层：

1. 数据有效性：预测日期、特征日期、价格日期一致；模型版本和特征版本存在；缺失或陈旧数据不进入榜单。
2. 可交易性：ST、停牌、退市风险、上市天数、涨跌停不可成交、异常价格、最低成交额和最低历史长度。
3. 风险预算：单行业上限、单板块上限、波动率上限、相关性约束、单票权重上限和组合最大换手。

推荐项不应只有 symbol 和 pred_score，至少增加：

    expected_return
    uncertainty 或 prediction_interval
    rank_pct
    horizon
    model_version
    feature_version
    as_of
    data_freshness
    tradability
    exclusion_reasons
    factor_reasons

其中 factor_reasons 可以复用 TreeSHAP Top-K，但必须标注“解释模型输出”，不能表述为因果关系。

验收条件：

- 首页推荐与选股页在相同日期、板块和 Top-K 条件下候选集合口径一致。
- 推荐榜不出现 ST、停牌、明确不可成交或数据过期标的，除非用户主动选择“研究模式”。
- 每个推荐结果都能追溯到模型版本、特征版本、预测日期、标签 horizon 和过滤原因。
- 推荐结果直接进入回测时，不会因为候选过滤口径变化而出现无法复现的净值。

### 7.4 P1-Q3：让训练目标更贴近“排序和交易”

当前 LGBM 的主要目标是未来收益回归，而产品实际使用是横截面排序。建议按 A/B 实验逐步比较，不要一次性替换生产模型：

1. 多 horizon 模型：分别训练 1、5、10、20 日模型，或共享特征的多任务输出；根据策略换手和持有期选择对应 horizon。
2. 排序目标：在保留回归基线的同时，评估 LightGBM ranking objective 或 pairwise ranking，使损失更贴近 Top-K 顺序。
3. 相对收益标签：在 xsec_demean 之外，增加市场、行业或风格中性残差收益，明确模型到底预测绝对收益还是相对收益。
4. 分类辅助头：对“未来收益超过交易成本阈值”建立二分类模型，输出概率和校准曲线；不能把回归分数直接 sigmoid 后当概率。
5. 稳健标签：继续保留极端收益质量报告，并比较 reject、winsorize、不同阈值对样本覆盖和 OOS 指标的影响。

每个实验必须使用相同时间窗口、相同 universe、相同成本参数和相同 promote 门禁。不要因为某个模型在单次测试窗口收益更高就直接替换生产模型。

验收条件：

- 至少完成 1/5/10/20 日 horizon 的滚动样本外对比。
- 新目标不仅看 RankIC，还要看 Top-K 超额收益、净 Sharpe、最大回撤和换手成本。
- 新模型在多数滚动窗口不劣于当前 LGBM，不能只在一个 test 段胜出。
- 任何模型替换都能回滚到上一生产版本。

### 7.5 P1-Q4：提高特征质量和因子组合稳定性

当前已有 alpha_basic_v2g 和真实 g1 图传导特征，这是继续提高信号质量的主要方向。建议：

1. 因子选择从“训练段整体 RankIC”升级为滚动窗口稳定性：统计每个因子的 IC 均值、ICIR、正 IC 比例、半衰期、换手和成本后贡献。
2. 做横截面标准化、行业/市值中性化和异常值处理，并把参数写入 feature_version，避免训练与推理隐式漂移。
3. 将 Factor Studio 中通过评估的自定义因子接入候选特征注册表，经过数据时点检查、缺失率、相关性、OOS IC 和成本门禁后才允许进入训练。
4. 增加特征稳定性检查：近期 PSI/KS、特征缺失率、分布尾部、训练/推理列集合和单位口径。
5. 对 g1 图特征分别做真实邻居覆盖率、行业边质量和图更新时点检查；图数据过期时要降级或拒绝训练，而不是静默使用旧图。

建议把因子加入生产模型前的最低门禁设置为：

- 至少 3 个滚动窗口有效。
- 多数窗口 RankIC 为正或方向符合预期。
- 换手和交易成本后仍有边际贡献。
- 与已有特征高度相关时必须证明增量收益。
- 没有使用未来行业分类、未来成分股或后验修订数据。

### 7.6 P1-Q5：从“选股准确”升级到“组合可交易”

预测排序正确不一定能赚钱，推荐组合还需要处理风险和成本。建议将 score 到权重的流程明确化：

1. score 先转成横截面标准分或分位，不直接用不同模型版本的原始分数混排。
2. 组合权重支持 equal、score_weighted、inverse_vol、risk_parity，并统一受单票、行业、板块、波动率和流动性约束。
3. 根据预测不确定性做权重缩放：高分但高不确定性的标的不能自动获得最大权重。
4. 将涨跌停、停牌、成交额、参与率、冲击成本、T+1 和印花税全部放进默认回测，而不是由用户手动打开后才计算。
5. 记录推荐进入、退出、持有期、换手、拒单原因和实际成交偏差，形成推荐到执行的反馈样本。

验收条件：

- 同一预测结果在不同初始资金下不会违反流动性约束。
- 净收益、净 Sharpe 和最大回撤都在默认交易成本下计算。
- 报告同时显示理论 Top-K、可交易 Top-K 和实际成交 Top-K。
- 推荐准确率提升但换手和成本恶化时，模型不会被自动判定为更优。

### 7.7 P1-Q6：滚动验证、市场状态和模型集成

现有策略回测已经支持 walk-forward，但 ML 训练还需要同样的滚动评估。建议：

1. 使用 expanding/rolling train window，每个窗口只用当时可见数据重训，在下一段 OOS 运行。
2. 按牛市、熊市、震荡、高波动、低流动性和板块环境分组评估。
3. 建立 LGBM 基线、ranking 版本、不同 horizon 版本的 champion-challenger 表。
4. GNN/TFT 只有在相同数据、相同切分、相同交易成本下稳定优于 LGBM，且残差具有互补性时才进入 ensemble 候选；当前 registry 中 GNN/TFT 专用加载器尚未接入在线 infer，不建议直接上线。
5. ensemble 采用验证段确定的固定权重或简单 rank average，禁止在 test 段调权重。

模型切换门禁建议：

- OOS RankIC、Top-K 超额收益、净 Sharpe 至少两项改善。
- 最大回撤、换手和成本不能显著恶化。
- 改善在多数滚动窗口成立，而不是由单一行情阶段贡献。
- 新模型 shadow 运行一个完整评估窗口后再 promote。

### 7.8 P1-Q7：校准置信度和线上反馈

当前 confidence 是模型级 RankIC 映射，不是单票上涨概率。建议分两步：

1. 短期：保留现有字段，但改名或增加 basis，展示模型级可靠性、评估窗口和适用 horizon，不显示“个股 80% 会涨”。
2. 中期：如果确实需要概率，训练收益阈值分类头，使用独立 calibration window 做 isotonic 或 Platt 校准，并报告 reliability curve、Brier score、ECE 和样本覆盖。
3. 对回归输出提供 conformal prediction interval 或分位数模型，展示预期收益区间而不是伪精确点估计。
4. 在线监控至少包括：近 15/30/60 日 RankIC、Top-K precision、分位收益差、换手、成本后收益、PSI/KS、预测覆盖率和数据新鲜度。
5. 只有 PSI 超标不能单独触发自动上线新模型；应同时检查信号退化、成本后表现和数据质量，失败则 quarantine 并回滚。

## 8. P2 体验、运维和长期治理

### P2-1：localStorage 用户态数据服务端化

涉及：股票自选、ETF 收藏、因子历史、组合导入和部分 UI 偏好。

建议：登录后以 user id 命名空间存储；localStorage 只作为未登录草稿或离线缓存；增加迁移版本、冲突合并和删除接口。不要把 admin token 当成普通用户偏好的一部分长期保存。

### P2-2：减少前端首包和 ECharts 解析成本

当前最大 chunk 约 694.56 kB，gzip 约 230.45 kB。建议：

- 按页面懒加载图表组件和 ECharts 模块。
- 只注册实际使用的图表和 renderer。
- 在 CI 输出 bundle size budget，超过阈值时提醒。

### P2-3：补充真实 readiness

/health/ready 不应只表达进程存活。建议区分：

- SQLite 是否可读写。
- DATA_ROOT 是否存在且可读。
- Redis 启用时是否可用；Redis 禁用时明确为 degraded 而非故障。
- 核心数据是否至少有一个可用快照。

### P2-4：Docker 生产化

生产配置建议补齐：非 root 用户、只读镜像层、secret 注入、日志轮转、数据和备份卷、健康检查、worker 数量、外部任务 worker，以及禁止把开发 token 写入镜像或 compose 默认环境。

### P2-5：导出和报告任务化

大文件导出、日报、回测报告建议统一走任务协议：生成、进度、失败、下载、过期和审计。API 不应长时间保持一个同步 HTTP 请求等待文件生成。

### P2-6：测试顺序和数据隔离继续加固

补测已解决生产目录污染，但仍应关注 test_lab_factor 产生的合成文件导致其他测试顺序敏感的问题。建议：

- fixture teardown 删除合成 predictions/features 文件。
- 测试数据使用唯一临时根目录，不依赖文件名是否碰撞。
- CI 加一次随机顺序运行，提前暴露隐性顺序依赖。

## 9. 推荐实施路线

### 第 1 阶段：安全和回归基线，1 至 3 天

- [ ] 确认 15 个公开计算接口的访问策略。
- [ ] 为需要保护的回测、研究、导出接口补后端 RBAC。
- [ ] 生产配置禁止默认 admin token 和派生 JWT secret。
- [ ] 重新运行 pytest、mypy、ruff、前端 typecheck 和 build。
- [ ] 增加生产配置检查、公开接口限额和错误契约测试。

阶段验收：权限注册表与产品决定一致；生产弱配置不能启动；测试可以重复运行且不污染 data。

### 第 2 阶段：数据中心和性能，3 至 5 天

- [ ] 用真实浏览器闭环验证 /data 的 overview、datasets、quality、logs、task-stats 和 status。
- [ ] 为 overview 的目录体积和数据集统计增加缓存或 manifest。
- [ ] 将强制刷新改成可观测的异步刷新。
- [ ] 增加冷算、缓存命中和单面板失败的前端回归。

阶段验收：正常进入 /data 首屏摘要小于 2 秒；单一请求失败不清空其他面板；冷扫描有进度和最后成功值。

### 第 3 阶段：长任务和前端数据层，1 至 2 周

- [ ] 引入任务表、lease、状态机和 task_id。
- [ ] 研究、回测、训练、日报、导出统一任务协议。
- [ ] 研究页改为按需加载。
- [ ] SWR 统一读取和轮询，移除重复的手写 setInterval。
- [ ] 统一 401/403/空态/降级/重试组件。

阶段验收：多 worker 不重复跑任务；页面刷新可恢复任务；研究首屏不触发重计算；无轮询泄漏。

### 第 4 阶段：量化口径和体验，1 周

- [ ] 确认并修正 Brinson benchmark weight 口径。
- [ ] 推广数据时效、覆盖率和来源披露。
- [ ] 处理 localStorage 用户态数据同步。
- [ ] 进行 bundle、Docker、readiness 和导出任务化优化。

### 第 5 阶段：量化准确率与推荐质量，2 至 4 周

- [ ] 将首页 AI accuracy 改为按 horizon 的 RankIC、Top-K precision、超额收益和成本后指标。
- [ ] 统一 market 推荐榜、screener、alerts 和 backtest 的候选过滤与 model/feature/as-of 元数据。
- [ ] 完成 1/5/10/20 日多周期和滚动 walk-forward 对比。
- [ ] 评估 ranking objective、市场/行业中性标签和因子稳定性筛选。
- [ ] 将 Factor Studio 因子接入受控特征注册表，不合格因子不得直接进入生产训练。
- [ ] 完成 LGBM 基线、ranking、多 horizon、GNN/TFT 候选的 champion-challenger 对比。
- [ ] 增加 Top-K 组合的行业、波动率、流动性、换手和交易成本约束。
- [ ] 建立 shadow 运行、模型校准、线上退化告警和自动回滚流程。

阶段验收：所有“准确率”数字都有明确 horizon 和样本口径；推荐榜不推荐不可交易标的；新模型必须在多个滚动 OOS 窗口中改善成本后指标，且可以一键回滚。

## 11. 最终判断

AQP 的功能广度和近期补测质量已经达到“可继续工程化”的阶段。当前最大的收益点不是再加页面，而是完成四个闭环：

1. 访问闭环：每个计算和写操作都有明确的认证、角色、限额和审计策略。
2. 数据闭环：数据中心真实展示数据、时效、缺口、来源和降级状态。
3. 任务闭环：长任务有 task_id、持久状态、租约、取消、重试和恢复。
4. 回归闭环：测试、类型、lint、浏览器回归和生产配置检查都能稳定执行。
5. 量化闭环：标签、预测、推荐、组合、成本和线上反馈使用一致口径，模型只凭样本外表现升级。

完成第 1 至第 3 阶段后，项目才适合继续扩大训练、实盘模拟和自动化调度范围。量化专项完成前，不建议把“AI 准确率”直接作为实盘决策依据；Brinson 归因、localStorage 同步和包体优化属于重要但不应抢在安全、任务治理和评价口径之前的工作。
