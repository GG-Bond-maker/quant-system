## 四、问题清单与修复方案

### P0-1 个股预测功能 100% 失败（核心功能不可用）

- **现象**：任意标的 `GET /api/v1/stock/{symbol}/predict` 均返回 `50000 系统异常: ValueError`（600519.SH 为数据不足的 51001，000001.SZ / 000002.SZ 均为 500）。
- **根因**：生产模型特征空间为 **v2g**（`features/version=alpha_basic_v2g`，88 列，含 43 个 `g1_*` 图传导列），而 `app/ml/predict.py:76` 只调用了 `build_factors(df)`（v1，45 列），**漏掉了 `apply_propagate()`**。正确链路见 `app/orchestrator.py:109` 与 `scripts/build_features.py:49`，二者均为 `apply_propagate(build_factors(raw))`。
- **证据**：`app/ml/infer.py:50 raise ValueError(f"特征列缺失: {missing[:10]}")`，缺失列 `['g1_vol_10','g1_vol_60','g1_atr_14',...]`。
- **修复方案（二选一，建议 A）**：
  - **A（对齐训练口径）**：`predict.py` 改为 `feats_df = apply_propagate(build_factors(df))`。需注意单标的 propagate 的构图开销与"邻居缺失导致 g1_* 全 NaN"的语义风险（训练时是真实邻居），建议补一个"特征列与模型特征严格一致 + 图列非空"的回归测试。
  - **B（规避图依赖）**：把生产模型切换/重训为 v1 特征空间（45 列），代价是放弃图传导因子。
- **回归测试建议**：断言 `set(model_feats) - set(feats_df.columns) == set()`，防止模型与特征再次漂移。

### P0-2 `/api/v1/datacenter/sync/auto` 断链（前端静默失败）

- **现象**：GET / POST 均返回 `{"code":40400,"message":"Not Found"}`。
- **影响**：数据中心页 autoSync 开关与状态加载失效；前端 `DataCenter/index.tsx:481` 的 `catch { /* 降级 */ }` 会**静默吞掉错误**——用户点开关看起来生效，实际从未持久化，服务重启后回到默认 15:45。
- **根因**：端点在 `09aea21` 引入，在 `732f9ec`（T16 datacenter 下沉 services）重构中丢失路由注册；`AutoSyncRequest` 请求体类仍在（`datacenter.py:475`），但没有任何 `@router` 绑定。
- **修复方案**：在 `datacenter.py` 补两个路由（`GET` 返回 `{enabled, time, today_done}`，`POST` 写入配置），复用 `services/sync_service.py` 已有的 `_load_auto_sync` / `_save_auto_sync` / `_auto_sync_today_done`；同时把前端静默 catch 改为显式提示。

### P0-3 3 只标的行情数据只剩 4 个交易日

- **现象**：`daily_bar` / `daily_bar_qfq` / `daily_bar_hfq` 三个数据集一致地只有 **600519.SH、001232.SZ、001248.SZ** 三只标的为 4 行（2026-09-01~09-04）；其余 1154 只中位 1133 行、最全 2107 行。
- **影响**：贵州茅台（600519.SH，前端示例/自检常用标的）的 K 线、预测、风险面板全部不可用（返回 51001「需 >= 60 行」）。
- **修复方案**：对这 3 只单独重跑全量抓取（如 `python -m app.data.ingest.tasks` 指定 symbols，或 `scripts/update_daily.py` 定向补数），并在抓取后断言"写入行数不得小于覆盖写前的行数"，防止增量同步覆盖历史。

### P1-1 ETF 概览 500 / 空数据（外部源无降级）

- **现象**：首测 `50000 RuntimeError`；复测 `code=0` 但 `data={"prev": None}`（空）。
- **根因**：`app/data/etf.py:383 build_catalog` 中 `_tencent_us_batch()` 拉取美股行情（qt.gtimg.cn）**ConnectTimeout**，异常未被捕获，导致整个 ETF 目录构建失败。
- **修复方案**：把美股/港股行情块包进 try/except，失败时降级为"该市场行情暂不可用"并置空，**不影响境内 ETF 主流程**（境内 ETF 是主体，共 1377 只）。

### P1-2 个股面板 / ETF 详情响应超时（> 45s）

- **现象**：`/stock/{symbol}/panels` 45s 超时；日志中 `north`（东财北向）、`holders`（股东）块分别因 ProxyError / 全源失败而降级。
- **修复方案（已实施）**：面板各 block 本已并行（`asyncio.gather`）且具备 `unavailable` 降级能力，缺的是**整体超时上限**。已新增 `_PANEL_BLOCK_TIMEOUT`（默认 20s，`AQP_PANEL_BLOCK_TIMEOUT` 可覆盖）并用 `asyncio.wait_for` 给每块加独立超时；超时块降级为 `unavailable` 且**不写缓存**（避免把超时固化成陈旧缓存）。详见 §五。

### P1-3 CI 必红：mypy 131 错误

- `mypy app/ --ignore-missing-imports` → **131 errors in 22 files**（集中在 `app/ml/monitor.py`、`app/api/v1/{report,ops,app_settings}.py`）。
- 多数为类型注解不严谨（如 `monitor.py:82` 对 `Any` 做 timedelta 运算、`report.py:337` str/list 赋值混用），无直接功能影响，但会让 CI 的 mypy 步骤失败。
- **建议**：按文件分批收敛，或先对存量文件加 `# type: ignore[code]` 基线、增量严格化。

### P1-4 选股快照停滞 3 个交易日

- **现象**：`screener_snapshot` 最新日期 2026-09-07（仅 38 条），上一日 09-04 有 600 条；09-08 ~ 09-10 无快照。
- **前端影响**：选股页因此展示的是 3 天前的结果，且当日池子仅 19 只（正常应为 ~1127）。
- **修复方案（已实施）**：响应新增后端计算的 `freshness{as_of, expected, lag_trading_days, is_stale, note}`（按真实交易日历，"最近已收盘交易日"口径，**不参与缓存**）；前端据此渲染「落后 N 个交易日 · 日期」，取代此前仅"非最新"的模糊文案。
- **根因（修复期深挖）**：并非快照本身过期，而是**行情同步存在缺口**（`daily_bar` 09-07 仅 237/1157、09-08 起仅 3 只），导致特征面板/预测退化——详见 **§五·附**。数据回补需在常驻服务 + 可用网络下执行。

### P1-5 Redis 未启动，缓存降级

- 现象：`/health` 显示 `redis=degraded`，日志 `Redis circuit breaker OPEN for 60s`。
- **✅ 已解决（2026-09-11）**：容器改名为 **`aqp-redis`** 并改由 docker-compose 管理（原手工容器实名为 `redis`，与 compose 声明不符，已停用并删除；数据卷保留未动）。`docker-compose up -d redis` 后：
  - `/health` → `"redis":"ok"`；`/api/v1/settings` → `cache.ok=true / degraded=false / breaker.open=false`；
  - `aqp:*` 业务键实际落库（`kline` 600s、`money_flow/quote` 300s、`fundamentals/holders/north` 6h、`etf:snap:history` 60d），缓存不再只靠进程内 LRU；
  - 容器配置与 compose 声明完全一致：密码 123456、`maxmemory 256mb / allkeys-lru`、健康检查 `healthy`、端口仅绑 `127.0.0.1:6379`。
- **无需重启后端**：熔断器 `open_until` 到期后自动重新探测，实测**更换容器**期间后端同样零干预恢复（"手动重启后端"属过度要求，已订正）。
- **同步修复**：① compose `redis` 服务补 `--requirepass ${REDIS_PASSWORD:?}`（缺省直接报错而非静默起无密码实例）+ 鉴权型健康检查 + `expose`→`ports 127.0.0.1:6379` + `aqp-api` 注入 `REDIS_PASSWORD`；② `run.md` 验证命令补 `-a`（原命令对带密码容器只会返回 `NOAUTH`，与"应输出 PONG"矛盾）、创建示例补密码并改荐 compose 方式；③ `.env` 注释与 `.env.example` 补齐 `REDIS_PASSWORD` 口径。
- 详情见 `AQP_Redis启动与缓存链路验证_20260911.md`。

## 五·附、P1-4 深度排查：根因是**行情同步缺口**（非快照本身）

审核时只看到"快照停在 09-07"，修复期进一步逐层下钻，定位到真正的数据断层：

| 层 | 最新日期 | 覆盖标的数 | 说明 |
|----|---------|-----------|------|
| `daily_bar`（原始行情） | 2026-09-04 | **1156** | 正常 |
| | 2026-09-07 | **237** | ⚠️ 骤降 |
| | 2026-09-08 ~ 09-10 | **3** | ⚠️ 仅剩重抓过的 3 只（P0-3 补抓）|
| `features/version=alpha_basic_v1` | 2026-09-04 | 1127 | 无 09-07 分区 |
| `features/version=alpha_basic_v2g`（生产） | 2026-09-07 | **19** | ⚠️ 残缺分区 |
| `predictions` | 2026-09-07 | **19** | ⚠️ 由残缺面板推导 |
| `screener_snapshot` | 2026-09-07 | pool_size=19 | ⚠️ 榜单塌缩 |

**根因链**：`autoSync`（每日 15:45）与 `evening_routine`（17:30）都依赖**服务常驻**；本机未常开 → 09-07 起行情同步只覆盖部分标的、09-08 起几乎未同步 → 特征面板/预测/快照随之退化。`evening_routine` 以"当天日期"幂等，`startup_catchup` **只补监控/日报、不补数据流水线**，因此漏跑的交易日不会自动补回（架构性缺口）。

**结论**：这是**数据/运维问题**，不是代码 bug；代码侧已通过 §五 的 `freshness` 披露使其不再被静默误读。真正的修复是回补行情并重建流水线（见下）。

### 回补操作步骤（需在本机网络下执行）

```bash
# 1) 启动依赖与后端（容器名 aqp-redis，compose 管理，已验证）
docker start aqp-redis
cd backend && ./.venv/Scripts/python.exe -m uvicorn app.main:app --port 8000

# 2) 增量同步（按标的最末交易日自动回补 09-07~09-10，幂等可续传）
curl -X POST http://127.0.0.1:8000/api/v1/datacenter/sync \
     -H "Content-Type: application/json" \
     -d '{"mode":"incremental","resume":true}'

# 3) 重建特征/推理/快照（流水线子集）
#    或直接等 17:30 的 evening_routine 自动执行
```

> ⚠️ **沙箱内不可执行**：本会话实测 eastmoney（`push2his.eastmoney.com`）被网络层拒绝（`RemoteDisconnected`），仅 tencent/sina 可达，
> 单只回补耗时 ~8–14s；1157 只全量需 **4 小时以上**，故未在会话内执行。
> 另注：项目配置的本地代理 `127.0.0.1:54053` 当前不可达（`Unable to connect to proxy`），回补前请确认其已启动（或直连可用）。
>
> **建议的架构改进（后续）**：把 `startup_catchup` 从"只补监控/日报"扩展为"检测到 `predictions` 落后于最近已收盘交易日时，触发一次带数据同步的补跑"，从根上消除"停机即永久漏跑"。
