## 1. 项目快照与真实入口

实际技术栈比任务描述（Python + pandas + AKShare + 自研回测）更重：**FastAPI + SQLAlchemy(async SQLite) + Polars + pandas + Redis + LightGBM/torch + AKShare，前端 React+TS+Vite**。git 跟踪 302 个文件，后端 Python 约 3.4 万行，另有 92 个文件存在未提交修改。

真实入口（任务书中的占位符【填写真实入口】按实际情况确认）：

| 入口 | 路径 | 用途 |
|---|---|---|
| API 服务 | `backend/app/main.py`（uvicorn app.main:app） | FastAPI，lifespan 内启动 4 个后台调度任务 |
| 每日流水线 CLI | `backend/app/data/pipeline.py`（python -m app.data.pipeline） | update_daily→validate→build_features→infer→screener_dump |

## 3. 问题清单

严重度定义（按任务书）：P0 = 崩溃/结果错误（会导致回测结论不可信）；P1 = 明显缺陷/性能瓶颈；P2 = 代码坏味道/可维护性。子代理的原始评级与本报告最终评级不一致处已注明理由。

### P0

**P0-1 回测 API 缓存键参数不全，会返回"别人的"回测结果**
- 位置：`backend/app/api/v1/backtest.py:158-163`（`/run` 键拼了 18 个参数，**漏 `init_cash`**，而 init_cash 定义于 :30、参与计算于 :103）；`backend/app/api/v1/backtest.py:501-504`（`/strategy-run` 键**漏 `walk_forward` / `wf_folds`**，而这两者直接改变 base_overrides 与响应结构，见 :409-412）
- 为什么是问题：TTL 600s 内，两次仅 init_cash（100 万 vs 1000 万）或仅 walk_forward 开关不同的请求会命中同一键，后者拿到前者的净值曲线/持仓/成交，属"结果错误"。同类 bug 此前修过一次并在 `backend/app/cache/keys.py:14-15` 留有警告注释（recommend_k 必须入键），属复发型缺陷。
- 修复建议：两个键补全缺失参数；更彻底的做法是把全部请求参数 orjson 序列化后取哈希作为 params_key，杜绝手拼遗漏。

**P0-2 qfq 增量抓取导致复权基准漂移，除权后回测价格失真**（数据子代理评 P1，按"回测结论不可信"标准升为 P0）
- 位置：`backend/app/data/ingest/tasks.py:107-143`（`fetch_and_write_daily_bars` 默认 `adjusts=("", "hfq", "qfq")` 直接抓 akshare qfq 落盘，:116-118 注释自己承认"qfq 以最新价重算整条序列"）；`backend/app/api/v1/datacenter.py:657-670`（增量同步只抓最后交易日之后）；`backend/app/api/v1/backtest.py:210-214`（策略回测优先读 `daily_bar_qfq`）；`backend/app/api/v1/stock.py:155`（K 线 qfq）
- 为什么是问题：发生分红/送转后，akshare 新返回的 qfq 序列已重新定基，而 `write_partition` 只按日期追加，**存量历史 qfq 行保留旧基准** → 同一 symbol 的 qfq 序列前后两段不可比，MA 交叉等价格信号与区间收益在除权日附近失真。`backend/scripts/build_qfq.py:57-66` 的不变量校验正是针对该问题设计的，但增量写路径绕过了它。项目里已有正确实现 `backend/app/data/repair.py:185-223`（qfq = hfq / 最新因子）。
- 修复建议：采集口径去掉 qfq（只抓 `("", "hfq")`），qfq 统一由 `repair.build_qfq_dataset` 在每次同步后全量重建并纳入 pipeline/scheduler 步骤；或至少在 quality.check_factor_jump 识别到因子跳变时触发该 symbol 的 qfq 重写。

### P1

**P1-1 领域层反向依赖数据层并发起真实网络 IO**（架构子代理评 P0；按本报告严重度定义归 P1，但为架构侧最高优先级）
- 位置：`backend/app/domain/portfolio.py:37`（`from ..data.portfolio_source import ...`）；`backend/app/data/portfolio_source.py:1-17`（docstring 自述"从 domain 迁移出来以满足纯函数守卫"，但 domain 里的调用链还在）
- 为什么是问题：domain 层的承诺是纯函数、可离线测试；组合回测/归因执行时会发起真实 AKShare 请求，结果不可复现。守卫测试 `backend/tests/test_domain_purity.py` 的 FORBIDDEN_MODULES 只拦"直接 import akshare/sqlite3"，对"import app.data 间接 IO"是盲区，守卫形同虚设。
- 修复建议：价格序列由调用方（api/backtest 层）取好后作参数传入 domain；把"禁止 import app.data/ml/api"加入 AST 守卫规则。

**P1-2 universe 属性非 PIT + 退市/长停持仓按最后收盘价永久估值，净值高估**
- 位置：`backend/app/data/universe.py:151-159, 191-194`（用**当前** instrument 快照的 is_st/name/industry 回填全历史）；`backend/app/data/ingest/tasks.py:44-56`（upsert_instruments 无退市处理）；`backend/app/backtest/broker.py:178-197`（mark_to_market 收盘缺失时回退 `_prev_close`）；配合 `backend/app/data/universe.py:243-244`（volume=0 → is_halted=True，退市股永续停牌）
- 为什么是问题：(a) 历史 ST 状态用今天的口径 → 历史 5% 涨跌幅判定前视；(b) 已退市/长期停牌的持仓股票卖单被 halted 闸门永远拒绝、市值按最后一次成交价冻结计入净值，回测净值系统性高估且持仓无法出清。
- 修复建议：instrument 增加 delist_date / asof 快照；universe 标记 is_delisted；引擎对退出宇宙的持仓执行"末价强平"或按清算折价减记。

**P1-3 主回测 `/run` 的冲击成本与流动性闸门静默失效**
- 位置：`backend/app/data/universe.py:247-251`（universe_daily 落盘列**无 amount**）；`backend/app/api/v1/backtest.py:70, 98-107`（/run 把 universe_daily 直接喂给引擎）；`backend/app/backtest/broker.py:225-233`（参与率上限需 `row["amount"]`，缺失返回 None = 不限）；`broker.py:139-147, 300`（冲击成本 daily_amount=0 时返回 0）
- 为什么是问题：用户在 /run 开 `enable_friction=true` 后，滑点/衰减生效但冲击成本恒为 0、max_participation 无效，且响应里 `friction_costs.impact` 恒 0 无任何提示——回测偏乐观而不自知。对比：策略回测路径（backtest.py:453-465）对 ma_cross 明确披露了口径，主路径没有对应披露。
- 修复建议：universe_daily 增加 amount 列（universe 构建时已读 daily_bar，顺手带上），或在响应 liquidity 块如实披露"主回测未计冲击成本"。

**P1-4 datacenter 增量同步把"拉取全败"记为完成，断点续传永久跳过缺口**
- 位置：`backend/app/api/v1/datacenter.py:670-673`（`n=0` 仅告警仍 `completed.add(sym)`，:511-519 每 30s 持久化）；配合 `backend/app/data/ingest/tasks.py:129-143`（三口径异常全吞、return 0 不抛错）
- 为什么是问题：网络故障/限流批量失败后 resume 永久跳过这些 symbol，数据缺口静默固化，下游特征/回测样本缩水且无告警。
- 修复建议：n==0 不入 completed（区分 no_data / failed 两张名单）；`fetch_and_write_daily_bars` 返回 (written, failed_adjusts) 供调用方判定。

**P1-5 流水线产物非原子写 + "增量重建因子"实为全历史重算**
- 位置：`backend/app/data/pipeline.py:147-149`（features 直接 `to_parquet`）、`:185`（predictions）、`:231-233`（screener 快照）；同模式还有 `backend/app/ml/infer.py:105`、`backend/scripts/build_features.py:54`、`backend/scripts/run_backtest_real.py:52`；`backend/app/data/pipeline.py:128-150`（step_build_features 全量读入所有 symbol 全历史 → 全量算 → 全量重写所有年份分区）
- 为什么是问题：parquet_store 的核心纪律是 tmp→fsync→os.replace（parquet_store.py:411-435），这些写点绕过后，进程中断会留半写文件；走 `read_parquet_columns` 路径时坏文件被静默跳过 → 数据静默缩水。性能上：docstring 说"增量"，实现是每日全历史重算，是每日流水线的最大瓶颈（对 5000 只 × 多年数据不可扩展）。
- 修复建议：写点统一改走 parquet_store 原子写（repair.py 已示范可 import 复用）；特征改为"仅重算受影响年份/增量 append + asof 保证"，或至少把全量重建移出每日节奏。

**P1-6 五组包级循环依赖，全部靠延迟 import 掩盖**（架构子代理）
- 位置：`backend/app/domain/portfolio.py:37` ⇄ `backend/app/data/panels.py:29-31`；`backend/app/data/pipeline.py:132,157,162` ⇄ `backend/app/ml/monitor.py:286`、`backend/app/ml/predict.py:54`；`backend/app/data/pipeline.py:29-30` ⇄ `backend/app/db/init_db.py:47`；`backend/app/core/scheduler.py:129-130`（import api.v1.report / ml.monitor，违反 `backend/app/core/__init__.py` "不得依赖业务模块"的自声明）、`backend/app/core/quotes_hub.py:61`
- 为什么是问题：改任何一层都可能波及"下层"；core/api 环意味着路由改动影响调度器；ml 改动可能破坏数据链路。目前没有 ImportError 只是因为环上所有边都是函数内 import——一旦有人把 import 提到模块顶层即爆。
- 修复建议：调度/编排逻辑移出 core（新建 app/jobs 或 app/services）；pipeline 编排上移；init_db 的 ensure_columns 迁到 db 层自有迁移。

**P1-7 api 路由层承载大量业务逻辑 + 双轨数据访问**（架构子代理）
- 位置：`backend/app/api/v1/datacenter.py:468-540, 557-787, 888-960, 1175`（同步状态机/断点持久化/三个管道编排循环/后台线程/定时器全在路由文件）；`backend/app/api/v1/market.py:28`（import data 层私有符号 `_ak`）、`:33-43`（自建 `_ak_call` 重试，绕过 akshare_adapter 的全局限速与指数退避纪律）；34 处直读 parquet（如 `backend/app/api/v1/backtest.py:67-70` glob 分区布局，绕过 parquet_store 封装）、11 个路由文件裸 `import sqlite3`（alerts/app_settings/market/ops/report/research/watchlist/datacenter）
- 为什么是问题：与 api/__init__.py 自述"仅做参数校验 + 调用领域/数据层"相悖；分区布局变更需改 10 个路由文件；ORM 与裸 sqlite3 并存导致事务语义不一致；datacenter 的同步逻辑无法被 CLI 复用（backend/scripts/update_daily.py 与之平行存在即是症状）。
- 修复建议：抽 `app/services/sync_service.py`；AKShare 外呼收口到 akshare_adapter._safe_call；parquet 读取统一走 parquet_store，DB 统一走 db/session。

**P1-8 ma_cross 引擎与 broker 引擎规则口径分裂**
- 位置：`backend/app/backtest/ma_cross.py:154-206`（execute_target 无停牌/涨跌停/T+1 闸门，仅凭 open 有效即成交）对比 `backend/app/backtest/broker.py:236-321`（T+1/涨跌停/停牌/整手/参与率完整）；`backend/app/api/v1/backtest.py:456-465`（披露仅提"未计冲击成本"，未提规则闸门缺失）

- 修复建议：ma_cross 迁移到 strategy_base 框架（作为框架策略实现，逻辑等价复用 broker 闸门），保留旧引擎仅作对照。

**P1-9 信号分析（IC/分层）用不复权收盘价**

**P1-10 test_pipeline.py 在全量套件下挂起，破坏测试隔离设计目标**
