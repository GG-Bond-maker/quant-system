## 2. 新发现 / 残留问题

### ✅ R-1（原报 P2）｜**已复核为误报**——两条路由均已带角色守卫（风险关闭）
- **原报告**：称 `App.tsx:96`（`/dataquality`）、`App.tsx:99`（`/capacity`）两条路由未包 `RequireRole`。
- **复核结论（主理人直接读源码 + 比对文件时间戳）**：**守卫存在**。原报告把两行 **JSX 注释**误当成了 `<Route>` 行——实际路由在其下方：
  - `frontend/src/App.tsx:96` 是注释 `{/* /dataquality 的两个后端接口 ops/quality-scan(POST) 与 ops/lineage(GET) … */}` 的首行；
  - 真正的路由在 **`App.tsx:99`** → `<Route path="/dataquality" element={<RequireRole><Page><DataQuality /></Page></RequireRole>} />`
  - `frontend/src/App.tsx:102` 是注释 `{/* /capacity 的 desk/capacity(GET) 已需 researcher … */}` 的首行；
  - 真正的路由在 **`App.tsx:104`** → `<Route path="/capacity" element={<RequireRole><Page><CapacityAttribution /></Page></RequireRole>} />`
- **时间线澄清（误报根因）**：`App.tsx` 的 mtime = **16:14**（本轮 P2-3 由 Engineer 补守卫时写入）；QA 首次读该文件早于 16:14，读到的是旧版，因而产生本误报。§1 表格已按 16:14 之后的版本更正为"✅ 一致"（见 §1「前端调用点回归」）。
- **结论**：**无需 Engineer 处理，R-1 关闭。**

### ✅ R-2（原报 P3，**已修复**）｜P1-1 超时余量偏薄 → `OVERVIEW_TIMEOUT` 60s → 120s
- **现象**：`/market/overview?refresh=1` 真口径冷算 **49.53s**，`OVERVIEW_TIMEOUT=60_000` 余量仅 ~10.5s；股票池扩容至 2500 后冷算只会更长，60s 余量不足。
- **处置**：`frontend/src/api/market.ts:9` 的 `OVERVIEW_TIMEOUT` 由 `60_000` **提升至 `120_000`**，对齐 `backtest/*` 系列既有的 120s 约定（同一文件 `:45/:50/:59` 三处消费点自动生效，无需改动）。
- **验证**：`npx tsc --noEmit` 通过（见 §3 追加行）。

### ⚪ O-1（信息级）｜`/settings` 触发扫描时 announcements 数据集报 `ColumnNotFoundError('date')`
