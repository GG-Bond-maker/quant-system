# AQP 前后端功能审查与修改建议（历史审查版）

> 本文件保留首轮审查记录。请以后续执行为准，参阅根目录的《AQP 前后端功能审查与修改建议_执行版_20260911.md》；其中已吸收 2026-09-11 写端点补测、UI 验证和近期缺陷修复结果。

审查日期：2026-09-11  
项目：Alpha Quant Platform  
范围：后端 FastAPI/API/数据/缓存/调度/认证/测试，前端 React/Vite/路由/API 封装/核心页面，部署与工程化配置。

## 1. 审查结论

项目已经具备较完整的量化研究平台骨架：后端按 `api / domain / data / ml / backtest / services` 分层，前端覆盖市场概览、个股、ETF、选股、回测、研究、数据中心、执行中心、预警、日报、设置等功能；统一响应信封、SWR 缓存、Redis 降级、后台调度、JWT/RBAC、Prometheus 指标和 Docker 编排都有落点。

当前最值得优先处理的不是“缺功能”，而是以下四类工程风险：

1. 写操作和重计算接口的权限边界不统一，部分重资源 POST 接口没有后端 RBAC 保护。
2. 后台调度与长计算任务集中在 FastAPI 进程内，缺少跨进程互斥、任务队列和取消语义，生产稳定性存在天花板。
3. 测试链路当前在本机被 `torch` DLL 崩溃阻断，后端全量回归不能稳定完成。
4. 前端仍存在多套轮询与本地状态方案，部分页面尚未迁移到统一 SWR/服务端状态。

建议按 P0/P1/P2 三阶段推进：P0 先补安全边界和测试可运行性；P1 做契约治理与长任务治理；P2 再提升体验、性能和生产部署能力。

## 4. P0 高优先级修改建议

### P0-1 统一保护所有写操作与重资源计算接口

证据：

- `backend/app/api/v1/backtest.py:255` 的 `/backtest/run` 未挂 `require_role`。
- `backend/app/api/v1/backtest.py:631` 的 `/backtest/strategy-run` 未挂 `require_role`。
- `backend/app/api/v1/backtest.py:684` 的 `/backtest/signal-analysis` 未挂 `require_role`。
- `backend/app/api/v1/research.py:167`、`:192`、`:211`、`:280`、`:369` 等研究计算 POST 未挂 `require_role`。
- `backend/app/api/v1/portfolio.py:108` 的 `/portfolio/backtest` 未挂 `require_role`。
- 前端仅在部分路由上做守卫，如 `frontend/src/App.tsx` 中 `/studio`、`/dataquality`、`/desk`、`/capacity`、`/settings` 有守卫，但 `/backtest`、`/portfolio`、`/research` 仍可直接进入。

风险：

- 未登录用户或 viewer 可以触发 CPU/IO 密集计算，导致资源被耗尽。
- 前端守卫不能替代后端权限；绕过浏览器即可调用接口。

建议：

- 所有会写入数据、启动训练、启动同步、生成报告、执行回测/优化/压力测试的接口统一增加 `Depends(require_role("researcher"))`。
- 纯读取接口按 `viewer` 或匿名明确分级，不依赖“默认开放”。
- 增加一张“端点权限矩阵”测试，枚举所有 `POST/PUT/DELETE` 和重计算 `GET`，校验未登录、viewer、researcher、admin 的行为。

### P0-2 处理 `ADMIN_TOKEN` 与 JWT 密钥生产风险

证据：

- 默认 `ADMIN_TOKEN` 为公开值，见 `backend/app/core/config.py:152`。
- 当前逻辑仅记录告警，不阻断启动，见 `backend/app/core/config.py:167-173`。
- `require_auth` 仍允许持有 `ADMIN_TOKEN` 直接成为 admin，见 `backend/app/core/auth.py:114-122`。

风险：

- 若服务被绑定到非本机或部署时遗漏 `.env`，默认 admin 凭据可直接获得最高权限。

建议：

- `ENV=prod` 时强制校验 `ADMIN_TOKEN != DEFAULT_ADMIN_TOKEN` 且 `JWT_SECRET` 已设置，否则启动失败。
- 将静态 `ADMIN_TOKEN` 直通限制为 `ENV=dev` 或独立开关 `ALLOW_ADMIN_TOKEN_LOGIN=false`。
- 前端停止迁移旧版 `AQP_ADMIN_TOKEN` 为 admin 会话，或仅在开发模式提示一次迁移。

### P0-3 修复后端测试链路中的 Torch DLL 崩溃

证据：

- 本机执行 `backend\.venv\Scripts\python -m pytest -q --tb=short` 时，在 `backend/app/__init__.py` 导入 `torch` 预热 DLL 阶段触发 Windows fatal access violation。
- `backend/app/__init__.py:29-31` 只捕获 Python 异常，无法捕获原生 access violation。

风险：

- 全量测试不可运行，CI/本地回归可信度下降。
- 应用导入阶段加载可选重依赖，可能让非训练场景被 Torch 环境拖垮。

建议：

- 不要在 `app/__init__.py` 无条件导入 `torch`；改为训练 readiness 或训练入口按需加载。
- 增加环境变量 `AQP_PRELOAD_TORCH=false`，默认关闭；仅在确认 XPU 环境需要时开启。
- 对 Torch/XPU 能力检测使用子进程探针，避免原生崩溃杀死主进程。
- 测试默认 mock 或跳过 Torch 相关用例，单独提供 `pytest -m torch` 标记。

### P0-4 清理测试 lint，恢复 CI 红绿信号

证据：

- `ruff check app tests --select F401,F811,E9` 报 28 个错误，集中在测试文件未使用导入和一次重定义。
- 应用源码在该规则集下未报错。

建议：

- 运行 `ruff check tests --select F401,F811,E9 --fix` 后复跑。
- 将 CI 中 ruff 范围固定为 `app tests`，避免测试代码质量漂移。
- 对测试工具导入统一放入 `conftest.py` fixture，减少每个测试文件重复手工插 path。

## 5. P1 中优先级修改建议

### P1-1 将长任务从 FastAPI 进程内调度迁出

证据：

- `backend/app/main.py:55-72` 在 lifespan 内创建晚间例行、启动补跑、预警调度、自动同步、市场预热等多个后台任务。
- 注释已说明 `to_thread` 不可取消，见 `backend/app/main.py:69-70`。

风险：

- 多 worker 部署时每个 worker 都会启动同一调度任务，可能重复同步/重复训练/重复通知。
- 进程重启时运行中任务状态不完整，取消和重试语义有限。

建议：

- P1 阶段至少引入 SQLite 任务锁和 lease，保证单机多进程互斥。
- P2 阶段迁移到 Celery/RQ/APScheduler + 独立 worker，FastAPI 只负责任务提交和查询。
- 所有长任务统一返回 `task_id`，前端轮询/SSE 读取任务状态。

### P1-2 建立 API 契约治理

现状：

- 后端统一信封设计清晰，前端 `client.ts` 在 `frontend/src/api/client.ts:73-88` 解包业务数据。
- 但 TS 类型多为手写，接口变更容易前后端漂移。

建议：

- 从 FastAPI OpenAPI 生成 TypeScript client/types，至少覆盖 `stock/market/backtest/research/datacenter/desk/settings`。
- 为统一错误码维护 `errors.schema.json` 或共享文档，前端不要手写散落常量。
- 在 CI 增加“OpenAPI diff 检查”，破坏性变更必须显式确认。

### P1-3 前端统一数据获取、错误展示和轮询

证据：

- `frontend/src/api/swr.ts:13-14` 已写明迁移方向，但当前只有市场概览完整使用。
- `frontend/src/pages/Research/index.tsx:87-100` 首屏一次并发触发 11 个真实计算请求。
- 多处页面仍有 `setInterval`，如自选、执行中心、设置、数据中心、因子工作室。

风险：

- 页面切换和刷新时重复计算，用户感知慢，后端压力不可控。
- 不同页面错误展示不一致，业务错误码无法统一处理。

建议：

- 建立 `useEndpoint`/`useMutationTask` 两类 hook：读取走 SWR，写入/长任务走 mutation + task status。
- 研究页按象限懒加载，默认只取 overview；用户展开或点击运行才触发 IC/优化/压力测试。
- 全局错误组件区分网络错误、权限错误、数据缺失、外部源降级。

### P1-4 避免前端 `innerHTML` 拼装行情标签

证据：

- `frontend/src/components/charts/KLineChart.tsx:595-604` 通过 `innerHTML` 写入指标和成交量标签。

风险：

- 当前数据主要来自数值字段，实际 XSS 风险较低，但图表层未来一旦混入名称、公告、策略字段会扩大风险面。
- 与 React 状态模型不一致，后续难做主题、可访问性和测试。

建议：

- 把指标标签改成 React state 渲染的结构化数组。
- tooltip formatter 如需 HTML，应使用统一 escape 工具，只允许数值和白名单颜色。

### P1-5 数据与缓存可观测性继续结构化

现状：

- `/metrics` 已存在，市场概览有缓存命中埋点。
- 多个降级块已经有 `status/unavailable/reason/note`。

建议：

- 每个聚合接口统一返回 `blocks.{name}.{status,source,latency_ms,as_of,from_cache}`。
- Prometheus 指标增加外部数据源成功率、耗时、熔断状态、缓存命中率、后台任务状态。
- 数据中心增加“数据截止日、样本数、缺口、异常文件数、最新同步任务”的首页摘要。

## 6. P2 低优先级与体验优化

1. 文档编码与终端显示：普通 `Get-Content` 输出 README 出现乱码，建议统一保存 UTF-8，补 `.editorconfig`，并在 Windows 文档中提示 `chcp 65001` 或 PowerShell UTF-8 输出设置。
2. 前端包体：`echarts` chunk gzip 约 230 kB，可按页面进一步拆图表组件，低端机器上减少首进研究/概览的解析成本。
3. 用户态数据服务端化：自选股、ETF 收藏、因子历史、组合导入目前大量依赖 localStorage，建议登录后同步到后端。
4. Readiness 语义：`/health/ready` 当前只返回 ready，建议实际检查 SQLite 可读写、Redis 可选状态、核心数据目录可读。
5. Docker 生产化：当前 compose 更适合本机单机，生产需要非 root 用户、只读镜像层、secret 注入、日志轮转和备份挂载策略。
6. 报告与导出：为导出文件增加任务化生成、下载过期时间和审计日志，避免大文件阻塞请求。

## 7. 推荐实施路线

### 第 1 周：安全与回归恢复

- 给所有写操作和重计算接口补后端 RBAC。
- 前端 `/backtest`、`/portfolio`、`/research` 根据后端权限策略补守卫或降级只读。
- 关闭默认 Torch 预加载，恢复 `pytest` 可稳定运行。
- 修复 ruff 测试导入问题。

验收：

- `pytest -q --tb=short` 可完成。
- `ruff check app tests --select F401,F811,E9` 通过。
- 未登录访问所有 POST/PUT/DELETE 均返回统一信封认证错误。

### 第 2-3 周：契约与长任务治理

- 从 OpenAPI 生成前端类型和 API client。
- 研究页、回测页、训练页改成 task 提交/查询模式。
- 后台调度增加 SQLite lease，避免重复执行。
- 聚合接口补结构化 block metadata。

验收：

- 前后端类型生成纳入 CI。
- 长任务刷新页面后仍能恢复状态。
- 多进程启动不会重复跑同一 autoSync/evening routine。

### 第 4 周：体验与运维增强

- localStorage 用户态数据迁移到服务端。
- 全局错误/空态/降级展示统一。
- 数据中心补数据健康仪表盘。
- Docker/README/run.md 按真实生产与本机两套模式重写。

验收：

- 核心页面二次进入不触发重复重计算。
- 数据缺失、权限不足、外部源不可用都有明确且一致的用户提示。
- 文档在 Windows 与 GitHub 上均无乱码。

## 9. 总体判断

AQP 当前已经像一个可演示、可继续演进的全栈量化平台；功能广度足够，工程基本盘也不薄。下一步最划算的投入，是把“能跑”升级为“可控地跑”：权限边界清楚、测试随时能回归、长任务不会拖垮 API、前后端契约自动同步。完成 P0/P1 后，再继续扩功能会轻松很多。
