| 危险端点守卫 | 真实同步/训练/镜像重建被 monkeypatch 成 `AssertionError`，兜底"测试设计失效" | (autouse) |

### 2.3 四条安全约束（本套件的前提）

1. 全部跑在 `conftest` 的**隔离环境**（临时 `DATA_ROOT`/`MODEL_ROOT`/SQLite，Redis 关闭），不碰生产库与生产数据仓库；
2. 鉴权/RBAC 断言**天然无副作用**——FastAPI 先解子依赖，`40100/40300` 早于请求体校验与处理器；
3. 危险端点（`trigger_sync/fetch/train`、`build_mirror`、`start_training`、`_run_incremental/repair/rebuild`）加 autouse 守卫；
4. **不调用**任何外发网络的端点正常路径，只测其拒绝路径。

### 2.4 关键设计：注册表守护（防"假覆盖"）

`test_registry_matches_runtime_rbac` 把硬编码清单与运行时依赖闭包逐条比对。
写这套用例时它**当场抓到了自己的一次漏登记**——清单里漏了
`DELETE /api/v1/studio/factors/{factor_id}`（50 vs 51），否则该端点将静默不受任何覆盖。
这条"测试的测试"是整套覆盖率可信的前提。

## 四、修复清单（均已验证）

### D1（P1，已修复）`/ops/quality-scan` 抛未捕获 `FileNotFoundError` → HTTP 500

- **现象**：分区目录不存在时（全新安装 / 该数据集尚未同步），
  `base.iterdir()` 抛 `FileNotFoundError`，绕过信封契约变成裸 500。
- **位置**：`app/api/v1/ops.py:40`。原有的 `if not sym_dirs` 判空**晚于** `iterdir()`，形同虚设。
- **修复**：`iterdir()` 前补 `if not base.exists(): raise AQPException(ERR_DATA_EMPTY, ...)`。
- **同类排查**：全仓 5 处 `.iterdir()` 中，`parquet_store`/`quality`/`repair`/`datacenter` 均已有 `exists()` 守卫，**仅 `ops.py` 遗漏**。
- **验证**：撤销修复后 `test_ops_quality_scan_runs` 变红（`FileNotFoundError`），恢复后通过（**反向验证已做**）。

### D2（P1，已修复）`/desk/attribution` 抛 `ZeroDivisionError`

- **现象**：前端「容量与归因」页显示"网络错误，请检查后端服务是否启动"；
  直连返回 `{"code":50000,"message":"系统异常: ZeroDivisionError"}`。**默认口径即崩**。
- **根因**（已用脚本定位到具体数据）：
  ```python
  bench_close = pivot.ffill().reindex(rets_wide.index)   # ← 顺序错误
  ```
  `ffill()` 只作用于**基准源自己的索引**；基准源 `universe_daily`（到 2026-09-07）
  比组合依赖的 `daily_bar_hfq`（到 2026-09-10）**旧**，`reindex` 落在源最新日期之后的
  3 行整行变 NaN → `bench_close.iloc[-1]` 全 NaN（1157/1157）→
  `(iloc[-1]/iloc[0]-1).dropna()` 得空序列 → `1.0 / bench_sym_ret.size` → 除零。
- **修复**：3 处同款写法统一改为 `... .ffill().reindex(idx).ffill()`（reindex 后再 ffill），
  并在除法前补零长守卫（如实报"基准与组合窗口无重叠交易日"而非 50000）。
- **回归**：`tests/test_desk_attribution_benchmark.py`（4 用例）显式构造
  "组合新鲜 / 基准落后 4 个交易日"，三种基准口径全覆盖。
- **验证**：撤销修复后 `[universe_equal]` 变红（`ZeroDivisionError`），恢复后 4 passed（**反向验证已做**）。
- **实测**：修复后 `code:0`，组合收益 -4.94% / 基准 -11.57% / 超额 +6.62%，2.1s 返回。

### D3（P1，已修复）`/datacenter/mirror/status` 无缓存，稳定 21~23s ＞ 前端 15s 超时

- **根因**：`mirror_status()` 对 3 个镜像数据集各做一次 `_scan_source`，
  即**逐文件读取约 3.1 万个源 parquet 的 `date` 列**，且**完全没有缓存**。
- **影响**：`/data` 页 `TextDataPanel` 调用它 → 必然超时。
- **修复**：按本模块既有约定加 120s 进程级缓存；前端该调用超时放宽到 45s 覆盖首次冷扫。
- **验证**：`23.33s（冷）→ 0.018s（缓存命中）`，提速约 **1300×**；
  浏览器网络日志中该请求状态由"pending"变为 **200**。

### D4（P1，**未闭环**）`/data` 数据中心页全局数据状态长期显示 `—`

- **现象**：`/data` 页「存储总量 / 覆盖标的 / 已落库 / 最近更新」全为 `—`，
  「本地资产清单」显示"暂无已落库数据集"，且**间歇**出现"请求超时，请稍后重试"。
  而同一时刻接口直连返回**真实值**（`storage_gb 1.4`、`covered_with_data 1157`、
  `dataset_count 7`、`daily_bar 1,307,252 行`）。
- **已定位的部分**：
  - `GET /api/v1/settings` 冷算 **27~32s**；`GET /api/v1/datacenter/overview` 冷算 **28.8s**；
  - 分段计时：`_load_settings 0.01s` / `_dir_size 6.47s` / **`overview() 28.77s`** / `_system_status 0.50s`；
  - `overview()` 内部 = `_scan_all_datasets`（~22s，TTL 120s）+ `_dir_size(DATA_ROOT)`（6.5s，**无缓存**，
    每次调用都遍历 3.2 万个文件）；
  - 前端默认超时仅 **15s**（`client.ts:60`）→ 冷路径必然超时。
- **已做的缓解**：按本项目"聚合接口放宽超时"的既有约定，把 `/settings` 与
  `/datacenter/overview` 的单次超时放宽到 60s。**"请求超时"提示已能消除**（实测 1 → 0）。
- **仍遗留**：**超时消除后数值仍不填充**，且偶发超时计数非 0。
  网络日志显示该页发起 `overview`/`settings` 的同时还有其它 XHR 处于 pending，
  但 `/datacenter/datasets` **根本没被请求**（而"本地资产清单"依赖它）——
  疑似前端数据装载/状态分支问题，而非后端。**需前端侧继续定位，本报告不臆测结论。**
- **建议**：① 后端给 `_dir_size` 加 TTL 缓存、优化 `_scan_all_datasets`（避免逐文件 glob）；
  ② 前端排查 `/data` 页的装载编排（为何不发 `datasets` 请求、失败后是否有重试）。

## 五、已报告但**未修改**的问题（需产品/口径决策）

### D5（P2）Brinson 基准权重未归一，`benchmark_weight` 恒为 0

`app/api/v1/desk.py` 的 `universe_equal` 分支：

```python
bench_w = (bench_sym_ret * 0 + 1.0 / bench_sym_ret.size).reindex(sym_ret.index).fillna(0.0)
```

`.reindex(sym_ret.index)` 把"全 universe 等权"**截断成只保留组合内的 3 只标的**，
于是 `bench_w` 合计 ≈ 3/1157 ≈ 0.0026 而非 1；
而 `app/domain/attribution.py:brindon_attribution` **不做归一化**，
导致 Brinson 区块的 `benchmark_weight`/`benchmark_return` 整体塌缩为 ~0，
与顶层 `benchmark_return`（-11.57%）口径不一致。

**未改动原因**：正确修法需要把 universe 全部标的的收益并入 Brinson 的收益矩阵
（输出会从 1 个行业变成几十个行业），属**口径/展示设计变更**，且会改动对外数字，
超出"补测"授权范围。建议产品确认目标口径后再改。

### D6（P2）错误码 `4001` 与登记的 `ERR_PARAMS=40000` 双口径并存

全仓 **9 处** `fail(4001, ...)`（`datacenter.py` 5 / `market.py` 3 / `app_settings.py` 1），
但 `app/core/errors.py` 登记的是 `ERR_PARAMS = 40000`；`4001` 是未登记的裸字面量。
既有测试中已有 **4 条断言 `== 4001`**（`test_market_quotes.py`、`test_api.py`），
说明这是**已固化的双口径**，不是笔误。

**未改动原因**：统一口径是破坏性 API 变更，需与前端/调用方协调并同步改 4 条既有断言。
本报告已在 `test_datacenter_sync_auto_roundtrip` 中**同时接受两者并显式断言"必须非 0"**，
使该不一致进入回归视野。

### D7（P2）跨模块测试污染：`test_lab_factor` → `test_api` 顺序敏感 flake

- `test_lab_factor.py` 的模块级 fixture 会往**会话共享**的 `DATA_ROOT` 写入合成
  `predictions/`（8 只 `600001~600008.SH`）与 `features/`，teardown 只清 DB 行、**不删文件**；
- 之后跑 `test_api.py::test_screener_filters_and_order` 会因选股池被污染而失败
  （期望 `600519.SH` 居首，实得 `600004.SH`）。
- **实测因果**：`lab_factor → api` = 1 failed；`api → lab_factor` = 29 passed。
- **当前是否影响 CI**：**不影响**。默认按字母序收集（`test_api` 在 `test_lab_factor` 之前），
  且项目未装 `pytest-randomly`，所以全量 553 passed 是稳定的。
- **未改动原因**：属既有测试基建问题，与本次补测目标无关；修法（teardown 清理合成产物）
  需触碰另一个模块的夹具。**建议单独立项**——一旦引入随机化或调整文件命名，flake 会立刻显现。

### D8（P3，仅记录）`POST /studio/factors` 先加载 features 再校验表达式

无 features 时报的是 `51001 features 数据不存在` 而非"表达式非法"，对调用方略有误导。
但 `parse_expr(..., extra_fields=fields)` 的 `fields` **来自快照列**，加载是前置条件，
属**固有序**而非可轻易重排的缺陷；若要改善需先从 parquet schema 取列名。
