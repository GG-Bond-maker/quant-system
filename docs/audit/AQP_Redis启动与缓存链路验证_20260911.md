## 三、重要结论：掉线恢复后**不需要重启后端**

- `backend/app/cache/redis_client.py` 的熔断器 `open_until` 存的是**时间戳**，窗口到期后 `_ensure()` 自动重连；
  失败路径下每 60 秒重探一次，成功即 `_mark_ok()` 清零。
- 本轮**更换容器**的实测再次印证：停旧起新约 30 秒，运行中的后端零干预从降级恢复为 `ok`。

## 四、容器改名方案（为什么这么做）

调研结论：全机除 AQP 外**无任何项目引用容器 `redis`**（CodeMind 用 `codemind-redis`、ETF 用 `etf-redis`，各自独立），
改名安全。选择「compose 管理」而非单纯 `docker rename` 的原因：

1. **配置收敛**：`docker rename` 无法修改启动参数；而旧容器缺 `--maxmemory 256mb / allkeys-lru`（无淘汰上限）。
   由 compose 重建可让名称、密码、内存上限、健康检查、端口发布**全部与声明一致**，一份配置即事实。
2. **消除孤儿状态**：手工容器不受 compose 管，`docker-compose ps` 看不见、`docker-compose stop redis` 管不到。
3. **回滚简单**：旧容器数据在独立卷 `redis-data` 中，未删除；如需回退，`docker run -d --name redis -p 6379:6379 -v redis-data:/data redis --appendonly yes --requirepass 123456` 即可。

执行序列：`docker stop redis` → `docker rename redis aqp-redis-legacy`（腾出名字并保留回滚）→
`docker-compose up -d redis` → 验证通过后 `docker rm aqp-redis-legacy`。

## 五、本轮修复的 compose 缺陷（原「遗留项」）

| 缺陷 | 修复 |
| --- | --- |
| `redis` 服务无 `--requirepass`，与 `.env` 的 `REDIS_PASSWORD=123456` 冲突 | `command` 加入 `"--requirepass", "${REDIS_PASSWORD:?REDIS_PASSWORD 未设置，请在根 .env 中配置}"` —— compose 自动读根 `.env`，缺省**报错退出**而非悄悄起无密码实例 |
| 健康检查 `redis-cli ping` 无鉴权（配了密码必然失败） | 改 `CMD-SHELL` + `redis-cli --no-auth-warning -a "$$REDIS_PASSWORD" ping \| grep -q PONG`，密码经容器 `environment` 注入 |
| `expose: 6379` 仅 compose 网络可达，宿主开发后端连不上 | 改 `ports: "127.0.0.1:6379:6379"`（只绑回环，不暴露局域网；aqp-api 容器内仍走服务名 `redis` 直连） |
| `aqp-api` 未注入 `REDIS_PASSWORD`（若改了 redis 密码会把 compose 模式改坏） | environment 增加 `REDIS_PASSWORD=${REDIS_PASSWORD}`，与 redis 服务同源 |
| 运行容器缺内存上限/淘汰策略 | 新容器 `maxmemory=256mb / allkeys-lru`，实测 `CONFIG GET` 确认 |

另：`.env.example` 的 `# REDIS_PASSWORD=` 已取消注释（缺省会导致手工/容器密码错配），
`docker-compose.yml` 头部使用说明同步为 `docker-compose`（本机无 `docker compose` 插件，只有独立二进制 v2.39.2）。
