## 1. 执行摘要（TL;DR）

本次复审的结论是：**架构主干健康度较高，历史踩过的坑大部分已落地为"带注释的纪律"并被遵守；但三条红线各有 1~2 处真实偏离，其中 2 处属于必须立刻处理的 P0/P1。**

### 关键数字

| 指标 | 数值 |
|---|---|
| 后端 Python 文件 / 行数 | 211 个 / 约 12,462 行（`app/` 主包） |
| API 层文件 / 行数 | 21 个 / 7,738 行（占主包 62%） |
| 数据规模 | `daily_bar` 9,006 + `daily_bar_hfq` 8,993 + `daily_bar_qfq` 5,826 + `cs/` 6,321 ≈ 3.6 万 parquet |

| 历史纪律复核 | 6 项**仍然遵守**，2 项**部分回退** |

### 三条红线结论

1. **架构一致性 —— 中等偏离。** 依赖方向无环（`data⇄ml` 环已解开、`domain` 零外部依赖、`data/ml/backtest` 均不反向 import `api`）。但存在**两处新增/遗留的方向倒置**：`jobs/evening_routine.py` 反向 import `api.v1.report`；`main.py` lifespan 从 `api.v1.market/alerts` 拉起后台调度器。历史遗留的 akshare 越界（`datacenter._fetch_etf_bar`、`portfolio._search_assets`）**本次提交仍未修复**。

2. **数据真实性 —— 无造假，但有"披露未落地"。** 全仓扫描**未发现** mock/合成数据泄漏生产路径、未发现 fallback 分支在数据缺失时编造指标（磁盘水位/置信度/覆盖标的失败时均如实返回 `None`）。**真正的红线问题是反向的：后端已经产出了完整口径披露字段（`close_basis` / `feature_basis` / `label_price_basis`），前端一个都没消费**；同时 `feature_runs` 表里被硬编码写入了错误的 `feature_version="alpha_basic_v1"`（实际生产是 `alpha_basic_v2g`）。

3. **性能 —— 纪律守住了，但"冷路径"没解决。** `build_mirror` 的 `is_in + partition_by + 按年分批` 写法完整保留；`desk.py` 三处 `.ffill().reindex().ffill()` 正确且带零长守卫；`iterdir()` 前 `exists()` 全覆盖；screener `freshness` 先写缓存后加字段。**但缓存只是把 28.8s 的成本"摊薄到每 120s 一次"，第一个请求仍要同步等满 29s**，而 `/api/v1/settings` 内部直接调 `overview()` 把这条慢路径传染给了登录后的首屏。

### 三个最该立刻处理的问题

| # | 问题 | 为什么急 |
|---|---|---|
| **A-01** | `export.py:54` 在 async 端点里**同步调用** `_run(req)`（重跑整个回测） | 一个用户点"导出回测"就能让整个 API 事件循环停摆几十秒，所有在线用户一起卡死。旁边的 `export_strategy_backtest` 明明写对了 |
| **C-01/C-02** | 同步任务、晚间例行 pipeline、手动 `/mirror/rebuild` 之间**没有任何全局互斥** | 三者都会写 `daily_bar_qfq` / `cs/` 镜像。撞车时轻则镜像日期错乱，重则原子写互相覆盖。atomic write 只保证单文件不半截，不保证两个写者的先后顺序 |

### 4.4 新增组件契合度评估

#### `core/compute_guard.py`（并发守卫）

| 评估维度 | 结论 |
|---|---|
| 实现正确性 | ✅ 正确。`async def` + `yield` 被 FastAPI 当 dependency 处理，`finally` 里 release，异常路径不泄漏槽位 |
| 与架构契合度 | ⚠️ **部分契合**。放在 `core/` 合理（横切关注点），但作为 `Depends` 挂在路由上是"按端点白名单"的粗粒度方案，容易漏挂（已漏 5 个重端点，A-07） |
| 上限 2 是否合理 | ⚠️ `le=2` 是硬编码上限，64 核机器也无法上调；且**不管训练**（C-03），实际防不住打满 |
| 拒绝策略 | ⚠️ 直接失败不排队（C-05）；错误码与登录限流冲突 |
| **建议** | 升级为"管道级资源闸门"：训练/同步/镜像重建/重计算四类任务统一申请，配合 C-01 的互斥锁一起做 |

#### `services/task_store.py`（任务状态存储）

| 评估维度 | 结论 |
|---|---|
| 是否持久化 | ✅ **是 SQLite**（`background_tasks` 表），文档字符串明写"API 重启后仍可查询最终状态" —— 与 `_SyncState.completed` 的内存态形成对比，**这块比已知问题修得好** |
| 跨 worker 安全 | ⚠️ **部分安全**。有 `claim_task` 原子领取 + `lease_until` 抢占，设计上考虑了多 worker；但**无续期、无 reaper**（A-08/C-04），实际多 worker 下会出问题 |
| 进程重启后状态 | ⚠️ **会悬挂**。`_sync.task_id` 是内存态，重启后没人去更新那行 SQLite 记录 → 永久 `running` |
| 与 `compute_guard` 配合 | ❌ **无配合**。两者完全独立：guard 只管"当前有多少并发"，store 只管"任务状态"，拒绝时既不排队也不写 store |
| **建议** | 补 lease 续期 + 启动 sweep；把"被 guard 拒绝"也记一条 `status='rejected'` 的任务记录，让前端能看到"排队失败"而非裸错误 |

#### `core/config.py` 的 `ENV=="prod"` 守卫

| 评估维度 | 结论 |
|---|---|
| 已覆盖 | `ADMIN_TOKEN`（默认值 + 长度 ≥32）、`JWT_SECRET`（存在 + 长度 ≥32）、`ALLOW_ADMIN_TOKEN_LOGIN`、`CORS_ORIGINS`（禁 dev 地址） |
| 缺失 | `DEBUG`、`LOG_LEVEL`、`REDIS_ENABLED`、`REDIS_PASSWORD`、`SQLITE_URL`、`WARM_OVERVIEW_ON_STARTUP`、`USD_CNY_RATE`、限流是否启用（O-03） |
| 失败模式 | ✅ 正确（启动即 `raise ValueError`，fail-fast）；非 prod 下对默认 ADMIN_TOKEN 有 `logger.error` 告警（`config.py:192-196`），但**不阻断** —— 本地研究场景合理 |
| **建议** | 补齐 7 项；把"应告警但不应硬失败"的项（`REDIS_ENABLED=False`、`WARM_OVERVIEW_ON_STARTUP=False`）改为 metrics 打点 + 启动 WARN |
