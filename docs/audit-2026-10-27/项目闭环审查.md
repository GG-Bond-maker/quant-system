# AQP 项目闭环审查（2026-10-27）

审查基线：`7216b8e`，审查开始时工作区干净。以用户图片中的六层能力为需求，排除自然语言问答。图片及项目文档中的文字作为需求或待核实声明，不作为额外执行指令。本次仅新增审查报告、隔离复现脚本及验证日志，未修复业务代码、更新行情或改变生产模型。

**结论：已有较完整的研究平台骨架和部分贯通路径，但尚未完成可靠、可追溯的六层完整闭环。** 主要问题是特征与推理入口未统一、置信校准缺失、历史信号缺少模型可用时点约束，以及模拟交易的资金、拒单、费用和订单终态不一致。

采用 code-review 的 Standards / Spec 两轴审查，并参考 backtesting-frameworks、quantitative-research 的 PIT、样本外验证及成本纪律。用户要求全项目审查，因此基线为当前项目全量快照，而非某次提交的差异。两个审查轴由独立子代理检查，主审查复核代码、运行验证并汇总。P1 表示会使核心功能、风险控制或研究结论失真；P2 表示局部功能或可追溯性缺口。

## Standards：实现正确性与工程约束

### S1 · P1 · 在途买单绕过资金和集中度限制

位置：`backend/app/trading/paper.py:268`、`:302`。

下单检查只使用已经成交的现金和持仓，不冻结在途委托；撮合阶段也未再次约束买方现金。同一100万元账户连续提交三笔同股50万元买单均成功，实际调用撮合后现金为 **−497,682.02元**，持仓市值149.7万元。该问题不需要并发即可触发。

建议：在同一事务内核算可用资金、冻结资金及在途敞口；撤单释放，成交转账，并在撮合时再次校验。验收必须覆盖连续/并发多单与单股集中度，且现金不得因普通现货买入成为负数。

### S2 · P1 · 拒单仍被计为触发和已实现收益

位置：`backend/app/trading/conditional.py:147`、`:283`。

调用 `place_order` 后不检查 `ok`，条件单直接改为 TRIGGERED，网格直接增加交易次数和估算收益。隔离复现开启 Kill Switch：实际母单和成交均为0，条件单仍显示已触发且 `order_id=null`，网格显示1笔交易和 **1,000元已实现收益**。

建议：分开条件达成、报单成功、部分成交、完成、拒绝等状态；拒单不得推进持仓/网格层级。已实现收益只能来自真实成交及成本账本，不能从触发价格直接估算。

### S3 · P1 · 条件单/网格 API 主路径不可用

位置：`backend/app/api/v1/desk.py:902`、`:915`、`:941`、`:956`、`:969`、`:993`、`:1020`。

上述路径调用未导入的 `sync_session_factory`，实际调用两个查询函数均得到 NameError；异常分支还引用未导入的 `fail`、`ERR_PARAMS`、`ERR_NOT_FOUND`。前端已有对应调用，因此不是单纯未使用代码。

辅助网关也存在连接缺陷：`backend/app/trading/gateway.py:184`、`:229` 导入 paper 中不存在的 `submit_parent_order` / `cancel_parent_order`，连接后的下单、撤单均 ImportError。该网关尚未接到当前主下单API，应与主链路故障分开理解。

建议：复用已有 `_db()` / paper 会话入口，统一网关协议；补带认证的真实 API 成功路径与网关连接后报撤单测试。

### S4 · P1 · 回测和模拟盘重复扣冲击成本

位置：`backend/app/backtest/broker.py:363`、`backend/app/trading/paper.py:397`、`:476`、`:511`。

回测卖出先 `cash -= impact`，又在包含 impact 的 cost 中扣一次。复现卖出10万元：成交报告成本84.1623元，现金应增加99,915.8377元，实际增加99,912.6754元，正好多扣冲击3.1623元。

模拟盘成交价已经包含冲击，净值和账户又把冲击计入额外费用。三笔买单样例额外多扣116.45元。这会系统性压低净值，并使TCA与账本无法对齐。

建议：明确冲击反映在成交价还是独立费用中，仅计一次；增加“初始资金＋卖出回款−买入支出−显式费用＝现金”的守恒验证，并核对净值序列与账户摘要一致。

### S5 · P1 · 禁买池同时阻断卖出和紧急退出

位置：`backend/app/trading/paper.py:242`、`:629`。

禁买校验未判断买卖方向。隔离账户持有100股，加入ST禁买池后卖出返回 `ok=false`；紧急清盘也未能退出，却返回 `ok=true, liquidated_positions=0`。

建议：分别定义开仓禁令与退出约束，紧急操作报告逐标的结果及失败原因。验收须覆盖“持有后进入禁买池”的场景。

### S6 · P2 · 限价/对手价界面没有完整执行语义

位置：`frontend/src/pages/OrderDesk/index.tsx:147`、`:385`；`backend/app/api/v1/desk.py:256`。

页面维护 priceMode/limitPrice，实际只提交 form；请求模型无对应价格字段。用户选限价仍按 paper 的次日开盘机制撮合。

建议：从请求、持久化到撮合贯通价格条件，验证不满足限价不得成交。实现前界面不应让用户误认为限价已经生效。

### S7 · P2 · 整手残额使订单长期留在在途队列

位置：`backend/app/trading/paper.py:342`、`:421`。

每个执行日只能写一笔成交，但只有剩余金额归零才视为完成；整手余款常无法归零。复现三笔订单均保持 PART_FILLED，再次撮合新增0笔。默认仅扫描前50笔，长期残留会占用扫描窗口。

建议：定义拆单窗口结束及不足一手残额的明确终态，区分完成、部分完成后取消与继续等待，并避免历史残单阻塞新单。

### S8 · P2 · 逐策略模拟对照和执行反馈缺少持久化来源

位置：`backend/app/db/models.py:359`；`frontend/src/pages/OrderDesk/index.tsx:412`。

母单无账户、策略版本、模型、信号或回测标识，前端组合草稿来源没有随订单入库。全局账户和TCA展示已有，但无法可靠区分策略A/B的净值、比较回测与模拟执行偏差，或追踪一次推荐最终形成的收益与风险。

建议：持久化 account_id、strategy_version、model_version、signal/run/backtest 标识与决策时点。研究实验、调仓草稿、订单、成交及日报共用这些来源；建立相同资金、日期、基准和费用口径的策略对照。

## Spec：图片需求的缺失或错误连接

### R1 · P1 · README 推荐推理路径无法稳定进入回测

位置：`backend/scripts/infer.py:47`；`backend/app/api/v1/backtest.py:170`。

CLI只输出 date/symbol/pred_score，回测API必须有 model_version。使用临时特征和mock模型运行真实CLI main，确认三列落盘、无版本元数据。全新数据目录按README执行后会在回测处断链；若混有其他分区，也无法可靠隔离本次信号。

建议：CLI、orchestrator、历史实验调用同一推理服务，统一输出 model_version、feature_version、label_horizon、数据版本、信号产生/可用时点。

### R2 · P1 · 财务/文本因子与日常生产构建未贯通

位置：`backend/app/orchestrator.py:198`、`:243`；`backend/scripts/build_features.py:57`；`backend/app/ml/financial_factors.py:109`；`backend/app/data/text_ingest.py:385`。

生产构建路径只执行 `build_factors → apply_propagate`。build_financial_factors、attach_text_features 在 app/scripts 中没有生产消费调用；财务因子开关默认关闭。本机生产 v2g 面板也未包含 f_roe/f_revenue_yoy 等财务列。图中的估值、质量与基本面变化不能仅因存在财务模块而标记完成。

财务 fetch/save 同样未接入日常流水线，默认年份固定为2023/2024/2025。本机63,594条财报的最新报告期为2025-12-31。

建议：先修R3的PIT缺陷，再建立财务更新、公告时点、asof附加、特征版本升级、训练及推理的一致路径；估值所需市值/股本与每股口径也要明确定义。启用前应验证有效覆盖、缺失原因与样本外增益。

### R3 · P1 · 财务预约日被当作数值可用日，启用前必须修复

位置：`backend/app/data/ingest/financials.py:333`。

SQL的 `is_proxy_announce=0 OR NOT EXISTS(actual<=asof)` 使“截至asof尚未实际披露”的预约记录反而获准返回全部财务数值。临时库预约日4月1日、实际披露4月20日；asof=4月10日即读取 revenue=999 等数值。预约计划可提前知道，不代表财报内容已知。

当前财务因子未进入生产ML，因此这是**启用前的潜在前视路径**，不据此断言现有线上模型已经受污染。建议预约信息独立存储；财报数值只以真实披露及可用时点放行，更正版本保留可重放历史。

### R4 · P1 · 预测置信度校准尚未实现

位置：`backend/app/ml/predict.py:39`、`:175`。

confidence 使用 `clip(0.5 + 2×valid_rank_ic, 0, 1)`，同一模型所有个股同值。代码已经如实披露不是个股上涨概率，但这仍不满足图片中的“预测置信度校准”。训练产物中的 pred_level 描述或收益水平调整也不能替代概率/区间校准。

建议：先明确输出是横截面排名分数、超额收益预测、上涨概率还是预测区间。概率任务使用严格时间隔离的校准集并评估Brier/ECE；收益任务可输出样本外预测区间及实测覆盖率。不能直接把模型RankIC映射解释成个股置信概率。

### R5 · P1 · 模型训练时点约束未贯穿历史回测

位置：`backend/scripts/run_backtest_real.py:34`、`:99`；`backend/app/api/v1/backtest.py:153`。

历史脚本用当前生产模型对任意历史区间生成预测，未拒绝落入模型拟合/调参区间的日期，还写入正式 predictions 目录。API按模型版本筛选，却不校验该模型在信号时点是否已经可用。训练器已有三段切分和gap，执行引擎已有T−1信号，这两点不能阻止“用后来训练的模型回放过去”的前视。

此处确认的是允许错误回放及覆盖的路径，不据此认定所有现存回测或历史预测都已污染。

建议：保存 fit_end、模型可用时点与训练/验证区间，强制区分样本内研究和样本外评估。历史绩效使用滚动样本外信号；实验回填写独立 run/model 命名空间，不覆盖生产记录。

### R6 · P1 · 港股缺数仍报正常，实时数据可套上历史日期

位置：`backend/app/api/v1/screener.py:532`、`:535`、`:564`、`:632`、`:642`、`:679`。

mock行情源返回空：仍生成10只候选，默认score=0.1，status=ok、message=数据正常，coverage.available=0但ratio=1.0。读取的是实时行情，传入2024-01-02又会返回该历史日期；缓存键未带target，日期请求还可能互串。

建议：报价缺失不得产生看似正常的排名；按有效报价数计算覆盖率并降级。没有历史截面就明确拒绝历史请求，不得改日期标签冒充重放；缓存键必须包含所有影响结果的参数。

### R7 · P2 · 预测期限来自全局配置而非实际模型

位置：`backend/app/orchestrator.py:343`；`backend/app/ml/predict.py:113`、`:170`；`backend/app/ml/train_lgbm.py:546`。

模型训练允许 --horizon 参数并保存metrics.horizon，而预测响应/分区使用全局ML_LABEL_HORIZON（单股接口还可接收horizon）。当两者不同时，分数没变，却被标注为另一预测期限，影响用户解释与后续评价。

建议：从模型产物读取训练期限并验证请求是否兼容；不同期限应解析到不同模型，不能只改标签。

## 改进顺序与闭环验收

1. **先恢复正确性**：完成S1–S5与R1/R3/R5/R6，统一现金/成交/费用账本和成功状态；修复静态门禁发现的未定义符号。新增测试必须验证订单和真实成交，而不只检查界面或状态字符串。
2. **再统一研究与执行来源**：用一套特征/推理入口服务CLI、API和调度；信号、回测、调仓、母单、成交、账户及报告保存同一来源；完成残额订单与限价语义。
3. **补齐图片能力**：在PIT验收后接入估值/质量/基本面因子，补真正的置信校准，建立逐策略模拟账户及相同基准/费用口径的对照。
4. **最后做性能与维护优化**：减少CLI/调度/单股预测间的重复实现；回测按日期裁剪预测分区，避免每次读取全部历史；把数据时效、模型可用时点和端到端验收接入CI/日常运行门禁。先测量瓶颈再扩大缓存或引入任务基础设施。

两个值得测量的具体热点：`backtest.py:153` 在日期过滤前读取全部预测分区；`paper.py:501` 每次账户查询从全部成交重放，随后重读持仓行情并重建净值，预检/下单又会调用账户查询。数据量增长后可采用按日期读取、请求内复用、增量账本快照；快照必须能与完整成交账本对账，不能为了缓存速度破坏S1/S4所需一致性。本次没有对这两项做生产负载基准，不给出未经测量的加速倍数。

建议用一套可重复的验收场景证明闭环：真实或固定脱敏行情→当时可知财务/公告→版本化特征→样本外预测与校准→候选/理由/风险→含成本与仓位限制的回测→绑定同策略版本的虚拟账户→报单/拒单/撤单/部分成交→现金和持仓对账→策略/基准对照报告。另覆盖断源、重启、重复请求、缺数与非交易日；任何失败都要有明确状态，不能仍返回“数据正常”。

Standards轴共8项，最严重的是在途委托绕过资金限制；Spec轴共7项，最严重的是历史信号缺少模型可用时点约束（并有尚未接线的财务PIT隐患）。两轴分别计数，不把模块数量或测试数量当作闭环完成率。
