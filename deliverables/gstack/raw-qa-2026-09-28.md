## 1. 端点可用性静态校验

### 1.1 方法

不启动服务，用 Python `ast` 解析 `backend/app/api/v1/*.py`：

1. 提取模块级 `router = APIRouter(prefix=...)` 与全部 `@router.<method>(...)` 装饰器；
2. 还原完整路径 = `/api/v1` + `router.py` 的 `include_router` prefix + 模块自身 prefix + 装饰器 path；
3. 逐个 handler 做占位检测（剥离 docstring 后看语句数 / 是否 `pass` / `...` / 空字面量返回 / `NotImplementedError` / TODO 标记）；

5. `(method, path)` 分组查重；同 method 同段数路径做参数段 vs 字面量段的遮蔽分析；
6. 903 个跨模块 `from .x import y` 符号的目标模块解析（另见 §1.4）。

### 1.4 🔴 依赖可解析性：2 处断裂的相对导入（本次最重要发现）

对 `backend/app` 下全部 `from .(.)*x import y` 做目标模块解析，共校验 **903 个符号**，发现 **2 处断裂**。
两处都是**函数体内的延迟导入**（defered import），因此模块顶层 import 不会报错 —— 只有执行到该分支才炸，**CI 的 `ruff check --select F,E9` 也捕获不到这类错误**。

#### Blocker-1：`api/v1/alerts.py:494` —— 相对层级少了一级

```python
# backend/app/api/v1/alerts.py:493-497
elif metric == "source":
    from ..cache.redis_client import RedisClient      # ← 应为 ...cache
    s = get_settings()
    breaker = RedisClient.breaker_status()
```

- `alerts.py` 位于 `app/api/v1/`，`..` 指向 `app.api` ⇒ 实际解析为 `app.api.cache.redis_client`。
- 真实模块在 `app/cache/redis_client.py` ⇒ 需要 **三个点** `...cache`。
- **运行时实测证据**（`python -c "importlib.import_module(...)"`）：

  | 模块路径 | 结果 |
  |---|---|
  | `app.api.cache.redis_client` | `ModuleNotFoundError: No module named 'app.api.cache'` 🔴 |
  | `app.cache.redis_client` | 路径存在（本环境因缺 `loguru` 依赖失败，非代码问题） |
  | `ls backend/app/api/` | 仅 `__init__.py` 与 `v1/`，**确认无 `cache/` 目录** |

- **可达性（真实业务路径，非死代码）**：
  - `alerts.py:107` 显式允许 `metric ∈ ("disk", "pipeline", "source")`；
  - 前端 `frontend/src/pages/Alerts/index.tsx:149` 的下拉框把 `'source'` 作为**可选值暴露给用户**；
  - `frontend/src/api/alerts.ts:22` 类型定义 `metric?: 'disk' | 'pipeline' | 'source'`；
  - 调用链：预警调度 → `_check_data_health(rule)`（`alerts.py:397`）→ `elif metric == "source"` 分支。
- **实际影响**：`_check_data_health` 的调用点（`alerts.py:625`）外层有
  `except Exception as e: logger.warning(...)`（`alerts.py:627`），故**不会 500 崩溃**，
  而是**该规则每轮评估静默失败**，仅留一条 warning。
  ⇒ `metric="source"`（Redis 熔断预警）**创建后永不触发，且用户侧无任何提示**。
  对一个"预警"功能而言，静默失效 = 功能不可用，判定为 **Blocker**。

#### 🟡 Issue-2：`data/ingest/multi_source.py:43` —— 同样是少一级

```python
# backend/app/data/ingest/multi_source.py:31-45
def _standardize(df: pd.DataFrame, code: str, source: str) -> pl.DataFrame:
    ...
    from ..domain.a_share_rules import code_to_symbol   # ← 应为 ...domain
```

- `multi_source.py` 位于 `app/data/ingest/`，`..` 指向 `app.data` ⇒ 解析为 `app.data.domain.a_share_rules`（不存在）。
- 真实模块 `app/domain/a_share_rules.py:71` 定义有 `code_to_symbol` ⇒ 需 `...domain`。
- **运行时实测证据**：`app.data.domain.a_share_rules` → `ModuleNotFoundError: No module named 'app.data.domain'`；
  `app.domain.a_share_rules` → **OK**。
- **降级理由（非 Blocker）**：全仓检索 `multi_source` / `fetch_daily_bar_multi`，
  在 `backend/app/` 内**零引用**，仅 `backend/tests/test_multi_source.py` 引用。
  即该模块当前**未接入生产链路**（`docs/audit/AQP_最终项目综合评审.md:482` 描述其为"已有三源冗余框架"的规划中模块）。
  ⇒ 判定为**潜伏缺陷 🟡**：一旦有人把它接进 `app/`，数据摄取标准化直接 ImportError。建议修掉或删除。

### 1.5 重复路由 / 路径冲突

| 检查项 | 命中数 | 说明 |
|---|---|---|
| 同 `method + path` 重复注册 | **0** | 115 条路由两两比对，无重复 |

`search` 段数更短且不与参数段同位，安全。

> 修正判定逻辑（任一段字面量不同 ⇒ 不可能互相遮蔽）后归零。最终结论以修正后为准。
