## 2. 三个必须放弃的模块（详述理由）

### ❌ 2.1 成立日期 / 基金经理

**实测**：CN 目录 `1363` 只中，`inception` 与 `manager` **缺失率均为 100%**。

**为什么不能"先放着"**：参考稿的表格里这两项是**有值**的。
若照抄布局而不填值，会渲染成空白格或 `—`，用户会认为"功能坏了"；
若填占位文案（如"暂无"），则与"把缺失当正常"混淆。

**正确处理**：**从顶部指标行移除这两项**，改为展示**已有且真实**的字段
（如费率、托管费率、规模、追踪指数、上市交易所）。

### ❌ 2.2 讨论与情绪（用户评论帖）

参考稿展示的是**真实用户讨论帖**（含头像、"3 min ago"、评论正文）。

**本项目无此数据源**。现有 `sentiment` 块是
**基于基金公告标题的关键词统计**（`_build_sentiment_block` 调 `score_sentiment`），
是**派生指标**，不是用户讨论。

**两者语义完全不同**：把"公告情绪"渲染成"用户讨论帖列表"是**偷换概念**。
页面底部数据来源说明里**已经如实标注了**这一点，必须保持。

**正确处理**：保留「公告情绪」卡（如实命名），**删除"讨论"字样与头像/时间轴视觉**。

### ❌ 2.3 底部跨页 Tab

参考稿底部有「市场概览 / 行业ETF / 宽基ETF / 主题ETF / Smart Beta」Tab。
本项目**不存在这些子页面**（`/etf` 与 `/etf/:code` 两个路由，无子路由）。
照做会产生 5 个死链。

**正确处理**：放弃；如需横向导航，用**已存在的** ETF 中心筛选能力替代。

## 3. 布局建议（对齐参考稿 + 适配本项目约束）

### 3.1 参考稿布局 vs 本项目建议

参考稿是**三栏 + 底部多区块**的密集布局。本项目已有类似结构，但有几处**结构性问题**需借此机会修掉：

| 位置 | 参考稿 | 本项目建议 | 理由 |
|------|--------|-----------|------|
| 上区 | 左 K 线（2/3）+ 右资讯（1/3） | ✅ 保持现有 `xl:grid-cols-3` + `col-span-2` | 现有实现已对齐 |
| 顶部指标 | 单行 6~7 项 | 保持 7 列网格，**但替换掉 2 个无源字段** | 见 §2.1 |
| 中部 Tab 条 | K 线下方独立 Tab 条 | 🔴 **建议删除** | 现有 `KLINE_TABS`（基本信息/重仓明细/行业配置/资金流向）**点了没有任何反应** —— 纯视觉还原，无内容切换。这是"看起来能点但没用"的假交互 |
| 下区 | 5 卡片一行 | 保持"图表区 2×3 + 右侧信息列" | 现有实现已足够 |
| 左下工具栏 | 竖排绘图工具 | ⚠️ 可选，见 §4.2 | 需新增画线层 |

### 3.2 🔴 建议优先修掉的结构问题：中部假 Tab 条

```tsx
// 现状：state 变了，但没有任何区块消费 klineTab
const [klineTab, setKlineTab] = useState<(typeof KLINE_TABS)[number]>('基本信息');
...
{KLINE_TABS.map((tab) => (
  <button onClick={() => setKlineTab(tab)} ...>{tab}</button>
))}
```

`klineTab` **只被这个 Tab 条自己读写**，页面上没有任何地方根据它渲染不同内容。
⇒ **点击无任何视觉变化**，是典型的"假交互"。

**三个选项**（按推荐度排序）：
1. **删除**（推荐）—— 减少误解，页面更紧凑；
2. **接真内容** —— 让 `klineTab` 切换 K 线主图的指标（复用 `KLineChart` 的 `mainInd`）；
3. 保留但禁用并标注"建设中"。

## 6. ⚠️ 注意事项（必读，含本项目铁律）

### 🔴 6.1 三条不可触碰的红线

1. **不得用占位值冒充数据** —— 成立日期/基金经理 100% 缺失 ⇒ **移除该项**，
   而不是填 `—` 或编造。缺失必须**在结构上消失**，而不是渲染成空值。
2. **不得偷换概念** —— "公告关键词情绪"**不能**包装成"用户讨论"。
   页面底部已有如实披露，**必须保留**。
3. **不得为对齐参考稿而制造假交互** —— 假 Tab 条（点击无反应）、死链 Tab
   都属于"看起来能用但没用"，比"没有这个功能"更糟。

### ⚠️ 6.2 技术约束

- **不能整页重写**：`EtfDetail/index.tsx` 已 783 行，此前多轮优化都围绕
  "去空白带"（`flex-1 min-h-0` + `ResizeObserver`）。重写会丢失这些成果。
- **后端块预算 4.0s / 端点 4.5s**：`detail` 块级并发且每块超时 4s。
  **新增取数必须放进现有块内**，不要新开第 8 个块（会挤压其它块的预算）。
- **新增块前先查同名**：`BlockBase` 已有 `status` / `reason` / `coverage`；
  新块若用 `coverage` 之类同名不同型，前端 TS 声明合并会**悄悄收紧契约**。
- **图表取色走 `chartPalette()`**，`theme` 必须进 `useMemo` 依赖数组；
  `setOption(option, true)` 必须带 notMerge。
- **`volume` 缺失时传 `null` 不传 `0`** —— 0 会画出一根假的"零成交量"柱。

### ⚠️ 6.3 数据口径提醒

- **跟踪指数 86.4% 缺失**：`tracking_index` 在目录里 1177/1363 缺失。
  现有 `_build_tracking_block` 用 `resolve_tracking_index` 回退解析（实测 510300 可解析成功），
  **但不要假设所有 ETF 都能解析** —— 需要显示"无法识别跟踪指数"的降级态。
- ~~**资金流 `net_inflow` 单位存疑**~~ → ✅ **已定论，无问题**（见 §6.4）。
  **堆叠柱可以放心用四档字段**，也可以用 `net_inflow`（= 超大单 + 大单），二者同源同单位（元）。
- **资金流 60 条中有 6 条 `net_inflow == 0`**：需确认是"真零"还是"缺失冒充零"
  （本项目反复强调的 `0 冒充不可得`）。**若为缺失，必须传 `null`。**

### ✅ 6.4 量纲核对结论（2026-10-01 补做，已用恒等式实测）

先前"`net_inflow` 量级跨 6 个数量级"的疑虑，经**专门量纲核对**后**排除**：

| 核对项 | 方法 | 结果 |
|--------|------|------|
| `net_inflow` 是否等于四档之一 | 恒等式 `主力 == 大单 + 超大单` | ✅ **70/70 行全部成立**，残差 `0.00` 元 |
| 四档是否同源同单位 | 恒等式 `超大+大+中+小 == 0` | ✅ 58/70 成立（12 行残差为**百元级舍入**，相对 1e8 量级可忽略） |
| 是否误用净占比字段 | 检查 `f57`~`f61`（%）是否被读入 | ✅ 未读入；`_num(parts[1])` 等索引正确 |

**结论**：`net_inflow` 与四档字段**均为「元」且同源**，`net_inflow = 超大单 + 大单`（主力净额）。
先前观察到的"跨 6 个数量级"是**不同交易日之间的正常行情差异**（同一日内部完全自洽），
**不是口径错误**。⇒ **资金流堆叠柱可安全实现**。

### 🔴 6.5 核对过程中额外发现的一个真实缺陷：ETF K 线 `volume` 单位 = 【手】而非【股】

**这不是本页改版引入的问题，而是既有数据口径缺陷**，但**直接影响**参考稿里
"成交量副图"与"资金流 vs 成交量"的对照解读，故必须记录。

**实测证据链**（腾讯快照 `qt.gtimg.cn/q=sh510300`，2026-09-30 同一条记录）：

```
字段三元组:  price / volume / amount = 4.432 / 4,958,544 / 2,196,229,027
真成交额   = 21.962 亿（快照 amount 字段，与 catalog 的 2196229027.0 一致）
隐含股数    = amount / close = 495,539,040 股
隐含股数 / volume 字段 = 99.9364  ≈ 100
⇒ 腾讯原始 volume 字段单位 = 【手】(1 手 = 100 股)
```

**缺陷**：`backend/app/data/etf.py::fetch_kline`（第 533 行）把腾讯 `r[5]` **原样**写入
`"volume"`，**未 ×100**。而数据仓库 `daily_bar.volume` 的单位经实测确认为**【股】**
（`amount/(volume×close)` 恒等式 = 1.0007，见项目长期记忆）。

⇒ **同一字段名在两处单位差 100 倍**：

| 位置 | 字段 | 单位 | 证据 |
|------|------|------|------|
| `data/parquet/daily_bar` | `volume` | **股** | `amount/(volume×close)` = 1.0007 |
| `data/parquet/daily_bar_hfq` | `volume` | 股（同源） | — |
| `app.data.etf.fetch_kline` | `volume` | **手** ← ⚠️ | 隐含股数/字段值 = 99.94 |

**后果**：任何把 `fetch_kline` 的 `volume` 当作"股"去做成交额估算的地方，
会得到 **1% 的真值**（差 100 倍）。核对过程中确实出现过
「主力净流入 = 成交额 32 倍」这类荒谬比例，**根因就是这个 100 倍**，
而不是资金流数据本身有问题。

**修复建议**（**不要在本次 UI 改版里顺手改**，因为它会改变对外契约）：
1. **推荐**：在 `fetch_kline` 内 `×100` 归一到"股"，与仓库口径统一；
   同时全仓 grep `fetch_kline` 的所有消费方，确认没有地方**已经**按"手"做过换算
   （否则会变成双重换算 10000 倍）。
2. **最低限度**：在函数 docstring 与返回结构里**显式标注单位 = 手**，
   并给 `fetch_kline` 的输出加一个 `volume_unit: "hand"` 字段（不破坏既有键）。
