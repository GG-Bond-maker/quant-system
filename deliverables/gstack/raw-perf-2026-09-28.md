# AQP 性能瓶颈定位与优化建议（静态审查）

- 审查日期：2026-09-28
- 范围：`backend/app/`、`frontend/src/`、已有构建产物与既有后端日志。
- 方法：代码与文件布局静态审阅；从既有 `backend-run*.log` 提取已记录耗时。**未启动服务、未执行压测、未全量扫描 4 万 Parquet 文件。**
- 数据事实：`data/parquet/` 当前包含 36,500 个 Parquet，其中 `daily_bar` 10,921、`daily_bar_hfq` 10,924、`daily_bar_qfq` 10,919；全仓（含备份/测试目录）39,944 个。数据根已有 `.manifest.json`（约 208 KB）和 3,438 个 `cs/` 日期截面镜像文件。

## 结论摘要

主风险不是单一事件循环阻塞，而是「**小文件全量扫描 / 全历史物化**」与「**外部数据源受全局限速后的串行网络调用**」。项目已有不少正确的缓解措施：路由均为 `async def`、重计算多用 `asyncio.to_thread`、SQLite 开启 WAL、Redis/SWR 带 stale 与部分 single-flight、股票列表已使用日期截面镜像。但热点路径仍绕过这些优化：市场日频概览直接遍历 2,499 个当年分区乃至历史全量 HFQ，ETFs 列表一次请求会两次构建目录，模型按每个缓存未命中的预测请求重新从磁盘加载。

## 四、实施前验证清单

1. 在 Prometheus 增加/确认 `http_request_duration` 的 endpoint P50/P95/P99，并为 Parquet 读取记录 `files_opened`、`rows_read`、`columns`、`cache_result`；现有中间件已记录 HTTP 时长（`main.py:233-260`），但无法直接回答文件扫描规模。
2. 对 P0-1/P0-2/P0-3 以同一数据快照做 cold/warm 对照：检查结果字段、日期和行数完全一致，再记录 wall time、RSS、磁盘读取量；避免“优化”改变量化口径。
3. 对模型缓存做 promote 并发测试：切换 production model 后必须新版本立即生效，不能返回旧 Booster。
4. 用浏览器 Performance/Network 验证 ECharts 是否进入入口关键路径、ETF 首页实际请求数量、以及图表变更时是否产生重复 canvas/init；不能仅据静态 bundle 名断言首屏阻塞。
5. SQLite 对慢查询执行 `EXPLAIN QUERY PLAN`；本审查未做数据库读写或查询计划，不应据此新增索引。

## 五、审查边界与已验证的正向控制

- 本次未运行压测、后端、浏览器、全量文件遍历或 DB `EXPLAIN`；所有没有既有日志支持的时延均标为“静态推断”。
- FastAPI 的 115 个路由装饰器后均为 `async def`；未发现同步 `def` 路由被默认 AnyIO 线程池 40 线程限制的直接证据。
- SQLite 已启 WAL/busy timeout；不能无证据宣称“未开 WAL”。
- Redis/SWR 已有 TTL、degraded 短 TTL、shadow stale key、部分 rebuild lock；不能无证据宣称热点端点全部无缓存。
- `screener/stocks` 使用按交易日截面镜像、API 端分页上限 100，说明“全市场列表必然扫描 4 万文件/前端必然渲染数千行”的说法不成立。
- ECharts 采用 core + 组件按需注册，未发现直接全量 `echarts` import；问题是 chunk 体积与延迟加载策略，而非树摇完全失效。
